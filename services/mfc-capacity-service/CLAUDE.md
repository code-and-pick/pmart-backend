# mfc-capacity-service

서비스 책임의 정본은 `docs/architecture/service-map.md` 의 `mfc-capacity-service` 절이다. 여기에는 **이 서비스 안에서만 적용되는 규칙**을 둔다.

## 계약
- REST: `contracts/openapi/mfc-capacity-service.yaml` → `openApiGenerate` 가 `com.pmart.mfc.capacity.api.generated` 에 인터페이스·DTO 생성. `api/*Controller` 가 구현한다. 계약을 먼저 고치고 코드를 맞춘다.
- 이벤트: 발행·구독 목록은 service-map.md. 발행은 `EventPublisher`(Outbox, Debezium), 소비는 `InboxGuard` 안에서.

## 패키지
`com.pmart.mfc.capacity.{api, application, domain, infrastructure}` (service-architecture.md). Controller 에 업무 규칙 금지.

## 데이터
- 스키마 변경은 `src/main/resources/db/migration/V*.sql` 로만. 적용된 파일 수정 금지.
- 다른 서비스 테이블·엔티티 접근 금지. 동기 조회는 API, 상태 전파는 이벤트.

## 실행
```bash
./gradlew :services:mfc-capacity-service:check                      # 단위 + 통합(Testcontainers) + 계약 검증
./gradlew :services:mfc-capacity-service:bootRun --args='--spring.profiles.active=local'   # deploy/local 기동 후
```
로컬 포트 8303.

- **작업자·업무·근무(WK-02 입력, 2026-11-08, 계약 0.4.0, V5)**: `/mfcs/{mfcId}/workers`(`WorkerService`·`domain/WorkerRules`·`WorkerStore`) — 등록·업무 변경·상태 변경·근무 등록/취소는 그 센터 MFC_SUPERVISOR, 조회는 그 센터 운영자·서비스. **사용자 결정: 센터 관리자가 등록하고, 업무가 바뀌어도 로그인 정보는 그대로** — `mfc_worker`(열쇠 = workerId = 운영자 ID·표시명·상태·지금 업무 버전)와 `mfc_worker_duty`(버전마다 한 행: 작업 유형·온도대 자격·사유)를 나눴다. 상태 ACTIVE·SUSPENDED·LEFT 는 새 배정만 막고 로그인·센터 권한(auth)은 건드리지 않는다(`mfc_worker_state_change` 이력). 업무·상태 변경은 기존 배정을 지우지 않고 맞지 않는 ACTIVE 배정을 `affectedAssignments` 로 돌려준다. 근무 `mfc_worker_shift`([start, end) 최대 16시간, 겹치면 409 SHIFT_OVERLAP). 배정(`POST /assignments`) 강제 제약: 등록(422 WORKER_NOT_REGISTERED)·ACTIVE(WORKER_NOT_ACTIVE)·업무에 taskType(DUTY_NOT_ALLOWED)·요청 temperatureZone 자격(ZONE_NOT_QUALIFIED). 근무 밖은 막지 않고 `warnings: [OFF_SHIFT]`(앞뒤 하루에 근무가 하나도 없으면 판단 안 함, Q-09 미결). 장비는 아직 없다. 계정 존재 확인은 하지 않는다(auth 호출 없음).
- **배정 추천·확정(WK-09·WK-10, 2026-11-08, 계약 0.5.0, V6)**: `POST /assignment-plans`(`PlanService` → `infrastructure/CpSatPlanner`, OR-Tools CP-SAT Java, 네이티브 처음 쓸 때 로드·동시 2개) — 그 센터 MFC_SUPERVISOR, horizonMinutes 10~480. 입력: mfc-fulfillment `GET /tasks?state=READY,ASSIGNED,IN_PROGRESS`(호출자 토큰 전달, `plan.mfc-fulfillment-base-url`) — READY 가 대상, 나머지와 capacity 활성 배정 작업은 담당의 앞 점유(유형 분만큼 0분부터), ACTIVE 작업자·지금 업무(작업 유형)·근무(근무 등록자는 근무 안에서만). 정책값 `plan.task-minutes.<유형>`·`time-limit`·`packing-stations` 없으면 422 CONFIG_REQUIRED(유형 분만 없으면 그 작업 미배정 CONFIG_REQUIRED). 모델: 작업마다 적격 작업자 선택 구간 하나 또는 미배정, 작업자 NoOverlap, PACK Cumulative ≤ 패킹대, 목적(Q-08 전 임시) 미배정(늦게라도 하는 것보다 늘 비쌈) ≫ 약속 지연 분 ≫ 최대 부하 ≫ 시작 합, seed 고정. OPTIMAL·FEASIBLE = PROPOSED, 그 밖 NO_SOLUTION. 추천은 배정을 안 바꾼다. `POST /assignment-plans/{id}/commits`: PROPOSED 만, 작업 READY·같은 version·활성 배정 없음·작업자 적격·같은 업무 버전 재검사 — 하나라도 어긋나면 STALE(staleReasons) + 409 PLAN_STALE, 아니면 한 트랜잭션에서 항목마다 배정(plan_id) + `AssignmentPublished`(planId, source PLAN, 집계 키는 수동과 같은 `MANUAL:<taskId>` — 작업별 순서). 자동 확정 없음.

- **작업자 명단 ↔ 인사·권한 연결(2026-11-13 사용자 결정 "추천대로" + "센터 관리자는 작업자와 별개", V14·V15)**: `application/HrLinkService`, 규칙 `domain/HrLinkRules`, 저장 `infrastructure/HrLinkStore`(V15 `hr_employee` 인사 사본·`mfc_worker_grant` 권한 기간), 구독 `infrastructure/HrEventConsumers` — `employeeEvents-in-0` = platform.employee.v1(직원 사건 4개만), `authEvents-in-0` = platform.auth.v1(`GrantApplied` 중 역할 MFC_WORKER 만). **인사 등록만으로는 작업자를 만들지 않는다**(센터 관리자 ≠ 작업자 — 등록 사건에 역할이 없음): 인사 사건은 사본(사번·고용 형태·재직 상태, 늦게 온 옛 사건 버림)만 갱신, **그 센터 MFC_WORKER 권한(`GrantApplied`, centerScope 의 `MFC-…`)이 붙을 때** 작업자 생성(registered_by·주체 `employee-auth-service`, 표시명 = 사번, 정규직·알바 자격·업무 빈 집합 = 센터 관리자가 정해야 배정, 일일크루 PICK·PACK). 권한이 인사 등록보다 먼저 오면 기록만 하고 등록 때 만든다. 상태 = 퇴사 LEFT > 인사 정지 SUSPENDED > 권한 기록이 있는데 지금 유효한 권한 없음(시작 전·끝) SUSPENDED > ACTIVE — 내리는 것은 늘, 올리는 것은 마지막 상태를 자동 주체(`hr-service`·`employee-auth-service`)가 내린 경우만(센터 관리자가 멈춘 것은 그대로), LEFT 는 되돌리지 않음. 권한 기간 경계는 사건이 없어 `HrLinkService.sweep`(`pmart.capacity.hr-link.sweep-interval`, 기본 PT1M)이 맞춘다. **센터 이동** = 권한 A 끝·B 시작(BO-01)으로 따라간다 — 인사 소속 변경 사건은 쓰지 않는다. 권한 기록이 없는 직접 등록 작업자는 권한으로 멈추지 않음(인사 사건·고용 형태만 반영). 권한 조기 회수 사건은 아직 없음(요청 `service-requests/employee-auth-service.md` EA-1). V14 `mfc_worker.hr_version` 은 안 씀. 시험 `HrLinkIT`·`HrLinkRulesTest`.

## 이미지 (ADR-0053)
- **GraalVM Native 이미지로 만들지 않는다 — JVM 으로 실행한다.** OR-Tools(JNI + 미리 빌드된 `.so`) 때문. 다른 서비스가 Native 로 바뀌어도 이 서비스는 JVM(2026-11-10 사용자 결정).
