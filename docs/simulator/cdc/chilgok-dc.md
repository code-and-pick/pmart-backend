# 칠곡 DC — CDC 시뮬레이터 연결 결정 (CDC-1~)

CDC 시뮬레이터(저장소 `pmart-cdc-simulation`, 세션 "cdc 시뮬레이션")와 CDC 백엔드가 같이 쓰는 센터 사실·코드 규칙. 결정마다 날짜를 적는다. 업무 근거는 `docs/business/WMS-business-logic.md`(정본)와 `docs/business/WMS-dc-wave-business-logic.md`(보충). 회신은 `docs/handoff/simulator/cdc/`.

## 1. 고정값 (사용자 2026-11-24 — 바꾸지 않는다)
| 항목 | 값 |
|---|---|
| 이름 | 칠곡 중앙물류센터(칠곡 DC) |
| 주소 | 경상북도 칠곡군 지천면 산단터널로 240 |
| 면적 | 8,600평(약 28,430㎡) |
| 사용 층 | 건물 5~7층 |
| 보관 용량 | 520만 유닛 |

- 이 값은 **시뮬레이터 표시·목표값**이다. `WMS-business-logic.md` 378·430줄대로 위치별 적재 가능량(하중·슬롯 용량)을 이 숫자에서 나눠 만들지 않는다 — 칸 용량은 위치 마스터에 따로 등록한다.
- 참고(사실 기록): 우아한청년들 글에서 8,600평·520만 유닛은 **인천기지**의 값이고, 칠곡기지는 "영남권 담당"으로만 나온다. 사용자가 칠곡에 이 값을 쓰기로 정했다.
- 모든 결과물(도면·화면·시드)은 **사용자 제공 설계 가정·개념도이며 실제 센터·축척·구조·하중·소방·온도 적합성을 검증한 것이 아니다**. 실제 회사 이름·로고·실명 센터를 재현하지 않는다(사용자 제공 구축 명세서 0장·9장, 2026-11-25).
- 참고 문서: [CDC 구축 명세서(사용자 제공, 2026-11-25)](reference/2026-11-25-cdc-build-spec.md) — 단층·A/R/F 구역·5항목 주소·PPC 30곳 등 **이 문서의 결정과 다른 값은 쓰지 않는다**(사용자 2026-11-25 "칠곡 결정 유지"). 겹치지 않는 부분만 가져왔다: 위치 유형 TEMPORARY, 피킹면 최소·목표량은 기본값 없는 설정값, 위 표시 문구.

## 2. 현장 근거 요약 (2026-11-24 두 페이지 원문 확인)
사용자 지시 "이걸 절대 거스르지 말 것". 시뮬레이터 동작이 아래와 어긋나면 이 절을 따른다.

**알바몬 커뮤니티 "심심해서 쓰는 인천비마트 후기"(2024-02-09, 인천 남동 — 댓글: 고잔동 스마트복합물류센터 5층)**
- 건물 여러 층을 쓴다(쉬는 시간 8층·1층 흡연, 센터는 5층대). 상온·냉장·냉동이 부서처럼 나뉘고 일용직은 관리자가 그날 파트에 배정한다.
- **분배**: 알티(큰 카트)마다 지역명 종이. PDA 로 카트의 상품(야채) 바코드를 찍으면 PDA 에 지역별 수량이 뜨고, 그 지역 상자에 담은 뒤 **지역 바코드**를 찍으면 끝. 길목이 좁아 동선이 겹친다. 자잘한 야채가 많아 수량 실수가 잦다.
- **FC**: PDA 로 **지역 바코드**를 찍으면 어느 구역에서 어떤 물건을 몇 개 카트에 담을지 뜬다 → 가서 바코드 찍고 카트에 담는다. 무거운 상자만 모은 존이 따로 있다. 혼자 하는 일.
- **라인**: 자키(핸드자키)로 물건 든 박스를 가져다주면 카트에 옮기고 스캐너로 바코드를 찍는다 → 자기 라인 구역에서 **스캐너 색과 같은 불이 켜진 칸에 숫자만큼** 넣는다. 가장 바쁘다(뒤에 쌓인다). 하루 약 2만 걸음.
- 석간 13:00~22:00(쉬는 시간 15:30~15:45, 저녁 18:00~19:00, 20:30~20:45). 21시 뒤로는 일이 거의 없어 카트 밀기·**보냉팩 씌우기**·청소.

**우아한청년들 스토리 "퀵커머스 물류 근거지 인천 중앙물류기지"(2023-10-06)**
- 기지(DC)는 상온·냉장·냉동 상품을 입고·보관해 전국 **피패킹센터(PPC = 이 프로젝트의 MFC)** 로 보내고, 판매 불가·파손·폐기품을 회수한다. 인천기지 2023-05 개장 8,600평, 520만 유닛, 칠곡기지는 영남권.
- 자동화(상온·냉장·냉동 모두): **휠소터**(컨베이어 바퀴가 박스를 PPC별 롤테이너 쪽으로 보냄), **DAS**(PPC 로 갈 롤테이너에 빈 박스 → 상품 스캔 → 그 PPC 칸에 불과 수량 → 작업자가 넣음 = 후기의 "라인"), **DPS**(빈 박스가 컨베이어로 상품 쪽에 도착 → 진열 칸에 불과 수량 → 담음), **오토스토어**(큐브형, 로봇이 피킹해 작업자에게 전달).
- PPC 마다 취급 상품이 달라 PPC 맞춤 공급, **낱개 출고**도 한다. 콜드체인 — **커버 씌운 롤테이너를 그대로 트럭에** 싣는다. 기지 시계는 PPC **입고 시간**에 맞춰 돈다.
- 사진(9장): 통로 표지 `A10`·`A11`·`A12` 가 붙은 파란·주황 팔레트 랙(5단 안팎, 아래 단은 박스 피킹), 롤러 컨베이어·곡선 컨베이어, 롤러 위 DPS 선반, 초록 크레이트 야채 분배, 고속 셔터 도크로 보냉 커버 롤테이너 반출.

**작업 방식 R-18(사용자 2026-11-25 "만들어" — 1단계)**: 5층 A 냉동 = DPS, C·D = 박스 피킹, E·F·7층 G·H = FC 피킹(피킹 = 분류, 분류대 없이 바로 출고대기), 6층 = 라인(DAS)·야채 분배. 1단계는 계약 그대로 — 피킹은 TRF × 구역 pick-results, 나눠 담기는 화면에서만 SKU 를 합쳐 보이고 MFC 별 sorting-results(LPN 하나 = TRF 하나). 실제 묶음 피킹(여러 TRF 몫을 라인 버퍼로 MOV)·나눠 담기 실적·버퍼 칸은 2단계로, 1단계를 돌려 본 뒤 정한다(설계 원문 시뮬레이터 docs/design/cdc-design.md §5.4, 2c82880).

WMS 원문 0.6 대로 자동화 설비 자체는 구현하지 않고 **가상 설비 결과를 WMS 가 검증**하는 모델을 유지한다(휠소터·DAS·DPS·오토스토어는 시뮬레이터가 그리는 가상 설비, 백엔드는 결과 실적만 받는다).

### CDC-3 위치 코드 — 7구간 = 랙 위치 식별값 (사용자 2026-11-24)
`{센터}-{구역}-{층}-{통로}-{베이}-{단}-{슬롯}` — 예 `CDC01-C-5-02-24-3-1`(칠곡 5층 상온 구역 C 2번 통로 24번 베이 3단 왼쪽).
- WMS 부록 2 정책 14.2 의 `센터-온도구역-세부구역/통로-랙-베이-단-포지션` 7구간을 칠곡에서는 **둘째 = 구역 글자(CDC-4, 온도대를 함께 뜻함), 셋째 = 층, 넷째 = 그 구역 안 통로**로 읽는다(14.1 ④ "세부구역/통로 칸의 의미는 센터마다 하나로 정한다"). 그림의 `A-12-24-3-1`(Zone-Aisle-Bay-Level-Slot)은 화면 축약 표시일 뿐이다(14.1 ③).
- 계약 패턴(`cdc-location-service.yaml` `LocationCode`)을 그대로 만족한다: 통로·베이는 숫자 2자리, 단·슬롯은 숫자. 원문 예시의 `R018`·`B03` 같은 접두어는 쓰지 않는다.
- **MOV 번호는 위치 코드가 아니다** — `MOV-20261020-001` 은 재고 이동 묶음(문서) 식별값, DC Wave 문서의 `R01-01-101`·`B04-02-205` 는 예시 위치일 뿐 이 규칙으로 쓴다.
- 통로 번호는 센터·구역 안에서 유일(구역 글자가 코드에 있으므로 구역마다 01 부터).

### CDC-4 구역 글자 — MFC 시뮬레이터 기준 (사용자 2026-11-24 "MFC 시뮬레이션이 기준")
| 글자 | 뜻 | temperatureZone |
|---|---|---|
| `A` | 냉동 | FROZEN |
| `B` | 냉장 | CHILLED |
| `C`·`D`·`E` | 상온 | AMBIENT |
| `F` | 상온 인기상품 | AMBIENT |
| `G`·`H` | 생활용품·기타 | AMBIENT |

- 위치 코드 둘째 구간은 이 구역 글자다. 위치의 `temperatureZone` 은 글자에서 정해지고, 어긋나면 등록을 막는다.
- (2026-11-24 고침) 처음에는 MFC 백엔드 칸 코드의 **온도대 글자**(ADR-0042: A 상온·C 냉장·F 냉동)를 썼으나, 사용자 기준은 MFC 시뮬레이터의 **구역 글자**(냉동 A·냉장 B·상온 C~H)다. CDC 코드에는 온도대 글자를 따로 두지 않는다 — MFC 백엔드 코드 `C-B-…`(온도대 C = 냉장 + 구역 B)와 글자 뜻이 다르니 두 센터 코드를 섞어 해석하지 않는다.

### CDC-7 피킹 선반 (사용자 2026-11-25, 시뮬레이터 R-13)
- 사용자 결정: 팔레트 랙은 입고·적치 보관 자리이고, **박스를 뜯어 개별 MFC 주문에 맞춰 피킹·패킹하는 공간은 따로 — MFC 처럼 진열한 선반**이다.
- 선반 모양 = MFC 선반: 1.25m 유닛, 5단 × 3칸, **칸 하나 = SKU 하나**. 자리는 층마다 북쪽 띠(승강기·출고대기 줄 남쪽), 분류 설비는 그 동쪽(시뮬레이터 배치 — 도면 R-05 가 나오면 도면을 따른다).
- 위치 코드: 같은 7구간, **통로 61~89 = 선반**(구역마다 61 부터). 베이 = 유닛 번호(01~, 홀수 동쪽·짝수 서쪽), 단 1~5, 칸 1~3. locationType **PICK_FACE**. 예 `CDC01-C-5-61-03-2-1`. 통로 01~60 은 팔레트 랙(RESERVE), 90~92 는 CDC-5 그대로.
- 선반 통로(R-17 2안, 6616cc1 — DT 안): 5층 A 61~71(11)·C·D·E·F 각 61(1) / 6층 B 61~76(16) / 7층 G 61~74(14)·H 61~73(13). 통로 하나 210칸(베이 01~14 × 5단 × 3칸). 상온 선반 목표 몫은 7층 G·H 에 두고 5층 C~F 는 통로 하나씩(5층 DT 가 좁음). 앞 배치(dd3d185, 12,480칸)는 R-17 로 바뀜.
- **위치 목록 사본**(2026-11-25, 6616cc1 — R-17 2안): [`layout/chilgok-locations.json`](layout/chilgok-locations.json) — 시뮬레이터 `docs/layout/chilgok-locations.json` 에서 화면 좌표만 뺀 표. **31,880칸** = 팔레트 랙 RESERVE 19,584 + 피킹 선반 PICK_FACE **12,180**(냉동 A 2,310·냉장 B 3,360·상온 C·D·E·F 각 210·G 2,940·H 2,730, EACH 80) + STAGING 102 + 지하 접안 DOCK 14. 칸 용량 합 460만 + 오토스토어 60만(코드 미정, R-05) = 520만. 앞 사본 dd3d185(32,436칸)는 R-17 로 바뀜.
- 피킹면 최소·목표량(보충 MOV 기준)은 위치마다 넣는 설정값이고 기본값이 없다 — 비우면 보충 판단을 하지 않는다(CONFIG_REQUIRED).
- 흐름(시뮬레이터 제안, 백엔드 반영 예정): 할당은 FEFO, 같은 LOT 이면 선반을 먼저 잡는다. 팔레트에 잡힌 예약은 선반 보충(MOV) 뒤에만 Wave 를 배포한다 → cdc-inventory `move-postings`(지금 501)가 필요하다.
- 1단 피킹면이 SKU 수보다 적은 문제(명세서 3장: 1단 4,960 < 10,000 SKU)는 랙 1단을 피킹면으로 쓰지 않으므로 생기지 않는다 — 선반 칸 수가 피킹 SKU 수를 정한다.
- **SKU 와 선반 크기(사용자 2026-11-25)**: CDC 는 **MFC 와 같은 SKU 번호**를 쓴다(상품 서비스 SKU — "MFC랑 같은 sku로 해서 연동되게"). 선반은 **MFC 업무 문서 설계 10,900 SKU**(상온 5,450·냉장 3,270·냉동 2,180, `MFC-business-logic.md` 112줄)에 맞춰 **칸 하나 = SKU 하나로 10,900칸 이상**으로 늘린다(사용자 "10,900 설계에 맞춰 선반 확장"). 지금 3,120칸(냉동 A 480·냉장 B 720·상온 C~H 1,920)은 모자란다 — 온도대별로 냉동 A ≥ 2,180·냉장 B ≥ 3,270·상온 C~H 합 ≥ 5,450칸.
  - 백엔드 문법은 그대로 받는다(구역마다 통로 61~89 = 29통로, 베이 01~). 칸 배치·평수(8,600평·층 배치 안에서 랙을 줄일지)는 시뮬레이터가 정하고 위치 목록을 다시 내보낸다(백엔드 요청 B-1, 2026-11-25).
  - **시작 재고는 실제 있는 상품만**: LAN 상품 서비스에 등록된 SKU(기록상 504개, MFC 다섯 곳이 쓰는 것과 같음)만 칸에 넣고 나머지 칸은 비워 둔다. 상품이 등록되면 같은 규칙으로 채운다.
  - 넣기: `deploy/lan/seed/cdc_stock.py`(2026-11-25) — SKU 하나 = 선반 칸 하나 + 같은 구역 랙 기둥(1~4단, 기둥이 모자라면 선반만), 구역은 냉동 A·냉장 B·상온 C→H 차례(상품 분류 근거가 없어 SKU 번호 순), LOT A(선반·랙 1·2단)·B(3·4단), 수량 = 칸 용량, 소비기한은 시험값. 안전량 0·취급 켜기 포함. 승인 번호(초기 보유·안전량)는 실행 때 받는다.
  - 같은 LOT·같은 기한이면 **피킹 선반을 먼저** 할당한다(2026-11-25 cdc-inventory 0.5.0 — R-13 제안, WMS CDC-F-009 "동선 효율은 FEFO 뒤에만"). 재고 서비스가 cdc-location 위치 일괄 조회로 유형을 읽고, 조회가 안 되면 위치 코드 순(랙 01~ 이 선반 61~ 보다 앞)으로 잡는다. 선반에 모자란 몫은 랙에서 잡히므로 그 예약은 여전히 보충 MOV 로 선반에 옮긴다.
