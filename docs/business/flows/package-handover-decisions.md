## D-1 허가 만료 뒤 취소·재찍기 허용 — 가장 중요
- 문서(MFC 1553행): 허가 후 결과 불명·통신단절·허가 만료 → 실제 실행 여부 대사. "시간 만료만으로 취소 성공·새 인계 허가를 내지 않는다. 실제 미전달과 점유 해제 확인 후에만 다음 요청." (MFC 1551행: 인계 진행으로 점유한 포장은 불명 중 재배정 불가, 허가 만료가 전달 취소를 뜻하지 않음)
- 지금 구현: 확정 요청 없이 만료된 fence 는 끝 → 중지 진행·다른 라이더/같은 라이더 재찍기 가능. 재배정 때 이전 라이더 fence 도 바로 끝.
- 위험: QR 찍고 봉투를 들고 나감 → 앱 오류로 픽업 완료(확정) 못 누름 → 만료 뒤 고객 취소 → 시스템은 포장대에 있다고 보고 취소 복귀 작업, 실물은 라이더에게.
- 선택지: A 지금대로(취소 빠름, 위험 남음) / B 문서대로 — 만료 fence 는 "확인 필요", 점원이 "랙에 있음" 확인 전 취소·재찍기 모두 대기 / C 절충 — 같은 라이더·같은 배송 재찍기는 확인 없이, 취소·다른 라이더는 점원 확인 뒤.
- 권장: **C**. 필요한 것: fulfillment 점원 확인 API(포장 실물 확인 → fence 해제), 중지·재배정이 확인 전 PENDING.
- **결정(2026-11-08, 사용자 "C")**: 구현 mfc-fulfillment 0.4.4(V8).
  - 같은 라이더·같은 배송 다시 찍기 = 확인 없이. 다른 라이더 = 409 `FENCE_EXPIRED_UNCONFIRMED`. 중지 = PENDING. 재포장 = 409. 재배정은 이전 라이더 허가를 끝내지 않음(이전 라이더 확정 409 `NOT_ASSIGNED`).
  - 점원 확인 `POST /packages/{id}/handover-checks`: `AT_STATION`(포장대에 있음 → 허가 해제) / `TAKEN_BY_RIDER`(없음 → 허가 라이더에게 인계 확정 — 내 추천, 사용자 이견 없음). 판정 `checkRequired`·`lastCheck`.
  - 사용자 덧붙임: **중도 고객 취소는 아주 예외 — 고객센터를 통해서만 제한적으로 허용**. 그래서 이 대기는 드문 경우다. 지금 고객 자율 취소는 상품 준비 시작(PreparationStarted) 전까지만, 그 뒤는 시스템 취소만 있고 고객센터 취소 경로는 아직 없음 → case-service 요청 R-2.
  - 클라이언트 공지 `docs/handoff/clients/mfc-app/2026-11-08-clients-notice-handover-check.md`.

## D-2 판정 주체·운영 센터 유효시간
- 문서(MFC Q-01): 판정 주체·토큰 유효시간·불명 복구 승인은 Q-01 결정. "결정 없이는 실제 통합 운영 차단".
- 지금 구현: ADR-0006(상태 '제안') 안대로 mfc-fulfillment 가 판정, 유효시간은 센터 설정(기본 없음, LAN MFC-SEED-01 PT2M 시험값). 운영 센터는 값이 없어 인계 불가(CONFIG_REQUIRED).
- 정할 것: (a) 이 구조 승인 → ADR-0006 승인 처리 (b) 운영 센터 유효시간 값(QR → 포장 들고 → 픽업 완료까지 현장 시간).
- 권장: (a) 승인 — 별도 판정 서비스는 왕복만 늘어남. (b) 현장 기준 필요, 2~3분 정도.
- **결정(2026-11-08, 사용자 "그래")**: (a) ADR-0006 승인. (b) 모든 센터 기본 3분(`handover-fence-ttl.default: PT3M`, 센터별 값이 있으면 그것). LAN 시험값 2분은 지움.

## D-3 QR 전 가게 도착 필수
- 문서(Delivery §5.1): "가게도착 버튼 누르면 해당 주문건의 QR코드를 찍어야 픽업 완료 버튼 뜸", `가게 도착 → 픽업 완료 → 고객 도착 → 전달 완료`. GPS 만으로 픽업 완료 불가.
- 지금 구현: MFC 는 도착을 보지 않는다.
- 선택지: (a) MFC 가 RiderArrivedAtStore 투영 후 도착 전 QR 거절 / (b) 순서는 라이더 앱·delivery-execution 이 지키고 MFC 는 안 봄.
- 권장: **(b)** — 도착도 버튼이라 MFC 재확인이 막는 게 없고 의존만 는다.
- **결정(2026-11-08, 사용자 "MFC 문서대로")**: MFC 문서에는 라이더 도착 확인 규칙이 없다 — 외부 출하대기 랙에서 주문 바코드(QR) 확인 후 인계, 라이더는 내부 출입 없음(MFC 410·412·633행). 그래서 MFC 는 도착을 보지 않는다(= b, 지금 구현 그대로). "가게 도착 → QR → 픽업 완료" 순서는 라이더 앱·delivery-execution 몫(Delivery §5.1).

## D-4 제한 라이더
- 문서(Delivery 603행, BackOffice 557행): 단계 `정상 / 신규배차 제한 / 일시 중지 / 계약 종료`. "제한 시 라이더앱의 신규배차·수락·픽업 권한과 패킹앱의 인계 가능 여부 연동", "수행 중 상품은 안전한 전달·회수·재배정". 이미 배정된 건을 어느 단계가 막는지는 없음.
- 권장: 신규배차 제한 → 배정분 인계 허용 / 일시 중지·계약 종료 → 인계 막고 재배정. 구현은 MFC 검사 추가 없이 배차가 배정을 풀면(DeliveryAssignmentChanged) 기존 "이전 라이더 허가 끝"으로 막힘.
- **결정(2026-11-08, 사용자 "추천대로")**: 위 권장안. MFC 는 라이더 단계를 직접 보지 않는다 — 배차(delivery-dispatch/rider)가 일시 중지·계약 종료 라이더의 배정을 풀면(DeliveryAssignmentChanged) 그 라이더는 확정 409 NOT_ASSIGNED, 새 라이더는 이전 허가가 만료·점원 확인(D-1 안 C) 뒤 인계. 해야 할 일은 배차·라이더 서비스 쪽(단계 바뀔 때 배정 풀기·재배정).
- **변경(2026-11-14, 사용자 — RS-1 구현 전 답)**: ① **신규배차 제한도** 새 배차를 막고 **픽업 전 배정은 취소 후 재배차**한다(위 "신규배차 제한 → 배정분 인계 허용"을 바꿈 — 이제 세 단계 모두 같음). ② **이미 픽업한 배송은 끝까지 완료**한다(모든 단계). ③ 제한은 컴플레인이 기준 이상 쌓이면 시스템이 검토 대상으로 올리고 **백오피스 운영자가 확인 뒤 건다** — 승인 화면(BO-20) 전에는 운영자 API(rider `POST /riders/{riderId}/restrictions`). 구현: rider-service 0.3.0 `RiderRestricted` → delivery-dispatch `RiderEventHandler`(배정 풀기 reason `RIDER_RESTRICTED`). MFC 쪽 변경 없음(그대로 DeliveryAssignmentChanged 로 막힘). 검토 대상 자동 등록(누적 기준·컴플레인 원천)은 아직 — `service-requests/rider-service.md` RS-3.

## D-5 배차 요청 시점 (문서끼리 다름)
- Delivery §3.1: 점원이 포장 시작 때 포장 소요시간을 넣고 배차요청. "패킹시작·패킹완료·배차요청은 별도 이력". 라이더가 포장 끝날 즈음 도착.
- flows/order-checkout-saga.md §3: 출고 READY(포장 완료) 뒤 배차.
- 차이: 이르게 요청하면 대기 짧지만 포장 중 취소·결품 시 배차 취소 필요(슬라이스 7). 봉인 전 QR 은 이미 거절됨.
- 권장: 업무 원문(Delivery)대로 — 점원 앱 별도 "배차요청" 동작(포장 소요시간 필수). **추가로 정할 것**: 포장 완료까지 요청 안 했으면 READY 때 자동 요청할지.
- **결정(2026-11-08, 사용자 "추천대로")**: 점원 요청 `POST /shipments/{id}/dispatch-requests`(예상 포장 분 1~180 필수, PACK 시작 뒤) + 포장 끝까지 없으면 READY 때 자동 → `DispatchRequested`(MANUAL/AUTO_ON_READY), 출고당 한 번. mfc-fulfillment 0.4.5(V9). 배차 자체·포장 중 취소 때 배차 취소는 delivery-dispatch 요청 DD-1.
- **바뀜(2026-11-13, 사용자 "자동요청빼" — 클라이언트 BR-51, 사용자 2026-11-10 "배차는 무조건 직원 요청")**: READY 때 자동 요청을 뺐다 — **배차는 점원 요청만**. 요청 없이 READY 가 된 출고는 요청 없음으로 남고 점원이 READY 뒤에도 요청한다. mfc-fulfillment 0.4.11.

## D-6 픽업 완료 판단
- ADR-0006 결정 5: 사건 기반(모든 포장 PackageHandedOver → 픽업 완료). delivery-execution 계약 초안: 픽업 완료 버튼 API. Delivery §5.1: "인계 확인 후 픽업 완료 가능".
- 권장: 합침 — 픽업 완료 버튼이 포장별 인계 확정(`handover-commits`)을 부르고, 배송 PICKED_UP 은 모든 포장 인계 사건이 왔을 때만. 버튼만 눌리고 재고는 안 준 상태가 생기지 않음.
- **결정(2026-11-08, 사용자 "추천대로")**: 위 권장. MFC 쪽은 이미 있음(handover-commits·PackageHandedOver) — 할 일은 delivery-execution 요청 DE-1.

## D-7 인계 후 취소 회수비
- 문서: `[결정 필요]`(cancel-vs-handover). 지금은 인계 뒤 전체 중지를 거절하므로 막히는 것 없음. 클레임 회수·반품 흐름 만들 때 고객 부담 / 회사 부담 / 사유별 중 선택.

## D-8 재고가 거절한 인계
- 지금: 포장 REJECTED, ERROR 로그, 재인계·취소 모두 막힘.
- 문서(MFC 1551행 표): 실제 사실 삭제 금지, 승인 정정/복구 전 자동 재개 금지.
- 권장: 운영자 재시도 API(취소 복귀와 같은 방식) 먼저, 화면은 BO-12. 절차 "실물 확인 → 재고 정정 → 재시도". 재시도 API 는 자동 재개가 아니라 운영자 행위라 결정 없이 선구현.

## D-9 작은 것
- 10kg 분할: D6-2 로 지금 주문당 출고 1개. 분할 도입 때 결정.
- 냉장·냉동 출하대기 한계(MFC Q-05): "인계 직전 단시간 이동"만 있고 한계 시간 없음.
- 문서 불일치: 취소 포장 상태 VOIDED(문서) vs INVALIDATED(구현, ADR-0046) — 구현명 유지. DeliveryType(사건 NORMAL/SPLIT/… vs API FORWARD/…)·DispatchFailed 사유 enum — 배차 서비스 만들 때 하나로.
  - **2026-11-10 정리(사용자 "그래")**: DeliveryType = FORWARD/RETURN/RESHIPMENT, DispatchFailed 사유 = NO_RIDER/REPEATED_REJECTION/EXPIRED/SYSTEM_FAILURE(사건 스키마를 API 에 맞춤). 포장: INVALIDATED = 재포장·피킹 뒤 중지, VOIDED = 밀봉 때 재고 거절(둘 다 구현대로, `mfc-states.md` 문구 고침).

## 2026-11-08 갱신 — D-1 결정 전 안전 조치
