## 1. R2 — 다음 작업 받기에 품질검사·적치 (mfc-capacity 0.14.0)

- `POST /mfcs/{mfcId}/workers/{workerId}/next-tasks` 가 mfc-inbound 입고 작업(READY·담당 없음)도 후보로 본다.
  - 업무 `INSPECTION` → 품질검사(`INSPECT`), `STOCK_MOVE` → 적치(`PUTAWAY`) 포함. 이제 이 두 업무에서 실제 작업이 온다(입고할 물건이 있으면).
  - 배정 응답 `taskId` = 입고 작업 `taskId`(`TSK-INS-…`·`TSK-PUT-…`), `taskType` = `INSPECT`/`PUTAWAY`.
  - `detail`: 한 줄 — `sku`·`lotId`·`qty`(남은 양 = 계획 − 완료)·`fromLocation`(수령 위치), `toLocation` 은 null(적치 칸은 현장에서 고름).
  - **상품명·바코드는 `detail` 에 없다** — 화면은 `GET /inbound-tasks/{taskId}`(mfc-inbound)의 `productName`·`barcodes` 를 쓴다(BR-53 R8 과 같음).
- **순서**(사용자 결정 2026-11-14, 업무를 안 골랐을 때와 `STOCK_MOVE` 안에서): 주문 피킹·패킹 → 자동 보충·긴급 이동 → **품질검사 → 적치** → 센터 관리자 이동 → 복귀. 같은 유형은 먼저 만든 것부터. Q-08 전 임시 순서.
- **담당만 실행**(사용자 결정 2026-11-14, mfc-inbound 0.9.0): 다음 작업 받기(또는 센터 관리자 배정)로 담당이 정해진 입고 작업은 담당만 `…/inspections`·`…/putaways` 를 할 수 있다 — 아니면 **409 `NOT_ASSIGNEE`**(이동 지시와 같은 코드). `InboundTask.assigneeId` 로 보인다. 담당 없는 작업은 지금처럼 그 센터 운영자 누구나.
  - 담당 기록은 배정 사건(Kafka)으로 mfc-inbound 에 닿는다 — 닿기 전 잠깐은 담당이 비어 있어 누구나 실행된다. 배정 직후 바로 실행해도 담당 본인이면 문제없다.
- 들고 있는 작업이 품질검사·적치면(아직 READY) 다시 불러도 그 배정 200(한 번에 하나).
- 조회가 안 되면(mfc-inbound 장애) 품질검사·적치는 건너뛰고 나머지 작업으로 — 업무 `INSPECTION` 만 골랐다면 409 `NO_TASK_AVAILABLE`.
- `InboundTask.createdAt` 추가(같은 유형 순서 근거).

## 3. R19-1 — 이동·실사에 상품명·바코드 (수용)

BR-53 R8 과 같은 모양: `productName`(상품 관리용 명칭, 모르면 null) + `barcodes[]`(활성 바코드 전부, 선행 0 보존, 모르면 빈 배열).

| 응답 | 서비스 | 필드 |
|---|---|---|
| `MoveOrder`(이동·보충 — 목록·단건·지시·집어 올리기·내려놓기·취소 응답 모두) | mfc-inbound 0.9.0 | `productName`, `barcodes` |
| `CountSession.sheet[]`(실사 계수표 — 만들기·조회·계수·결정 응답) | mfc-inventory 0.16.0 | `productName`, `barcodes` |

- 값은 mfc-inventory SKU 사본(상품 사건 투영)에서 온다. 이동 지시는 mfc-inbound 가 조회해 채우고, 조회가 안 되면 null·빈 배열로 두고 응답은 그대로(BR-53 과 같음).
- 새 쿼리 `withLabels=false`(이동 지시·입고 작업 조회)는 **서비스 간 조회용**(mfc-capacity — 동기 호출 2 hop 규칙). 앱은 쓰지 않는다(기본 true).
- 바코드 스티커 재출력(§2 알림)에 `barcodes[0]` 를 쓰는 것 — 백엔드 쪽 할 일 없음, 확인함.
