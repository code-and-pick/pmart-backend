# 요청 — 문의·대화에 쓸 수 없는 말이 있으면 안내 문구 보이기 (422 BLOCKED_WORDS)

보낸 영역: backoffice
- 작성: pmart-backend PC 2(backoffice), 2026-11-23
- 받는 앱: **customer-app**(고객 문의 남기기), **rider-app**(라이더 문의 남기기·문의 대화 이어 쓰기)
- 근거: 사용자 결정 2026-11-23 — "A는 문의나 채팅에 입력 자체가 안 되게 해주고, C는 걸리면 정지되는 걸로 해줘. B도 해줘"(욕설은 막기만 하고 정지는 없음, 적용 범위는 "문의 + AI 채팅 + 라이더 문의 대화"). 서버 요청서 `docs/architecture/service-requests/case-service.md` R-14, `customer-service.md` CU-7.
- 서버 상태: case-service **0.37.0**(백엔드 PR #376) — **병합·배포 전**. 금칙어 목록은 배포 뒤 PC 1 이 설정에 넣는다. 그 전에는 이 오류가 나지 않는다.

## 서버가 하는 것
- 아래 세 요청의 글(문의는 제목·본문, 대화는 본문)에 **막기 단어(욕설)** 가 있으면 글을 받지 않고 **422** 를 준다.
  - 고객·라이더 `POST /api/v1/inquiries`
  - 라이더 `POST /api/v1/inquiries/{inquiryId}/messages`
- 응답 본문(Problem Details — 다른 오류와 같은 모양):
  ```json
  {"type":"about:blank","title":"…","status":422,"code":"BLOCKED_WORDS",
   "detail":"쓸 수 없는 말이 들어 있어요. 고쳐서 다시 보내 주세요.","traceId":"…"}
  ```
  - **어느 단어가 걸렸는지는 주지 않는다.** 목록은 서버 설정이라 앱에 두지 않는다.
  - 대소문자·띄어쓰기·문장부호는 무시하고 비교한다("씨 발", "씨.발" 도 걸림).
  - 저장되지 않으니 **같은 글로 다시 보내도 또 422** — 고쳐서 다시 보내야 한다.
- 정지 단어(위협·거친 말)는 막지 않는다. 글은 접수되고 서버가 따로 7일 정지를 건다. 정지 알림·로그인 막힘은 다른 요청(CU-7, 라이더 RS-8)으로 오고, **이 문서와는 따로**다.

## 앱이 할 것
1. 422 이고 `code` 가 `BLOCKED_WORDS` 면, 쓰던 화면에 그대로 머물며 **입력한 글을 지우지 않고** 안내를 보여 준다.
   - 문구: **"쓸 수 없는 말이 들어 있어요. 고쳐서 다시 보내 주세요."** — 서버 `detail` 을 그대로 써도 되고 앱에 같은 문구를 둬도 된다.
   - 위치: 입력칸 아래 오류 줄 또는 짧은 알림. 고객 문의는 제목·본문 중 어느 쪽인지 서버가 알려 주지 않으니 **본문 아래**에 보여 준다.
2. "다시 시도" 단추로 같은 글을 자동으로 다시 보내지 않는다(또 422).
3. 다른 422(예: 주문을 못 찾음 `ORDER_NOT_FOUND`)와 섞지 않는다 — `code` 로 나눈다.
4. 걸린 글을 앱 로그·분석 이벤트에 남기지 않는다(개인정보·욕설 원문).

## 확인 방법(배포 뒤)
- 서버 배포와 목록 반영을 PC 1 이 알리면, LAN 시험 계정으로 막기 단어가 든 문의를 보내 422 와 문구를 확인한다. 목록 값은 PC 1 에게 묻는다(저장소에는 적지 않는다).
