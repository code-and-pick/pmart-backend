# ADR-0093 상담 도우미 — 고객 연락 접수 화면 옆에서 본인 확인·정책 근거를 먼저 보여 준다

- 상태: **승인** (2026-11-28) — 기본값(결정 4·6)은 사용자 확인 대상으로 남긴다
- 근거: 사용자 2026-11-28 "백오피스 운영도우미에서 고객쪽 인입이 왔을때 해당 상담사를 돕는쪽이 필요한것같아. 기존 백오피스 화면처럼 질문과 대답하는 구조도 좋은데 클라이언트 작업도 먼가 달라져야할것같고" → 추천("채팅이 아니라 상담 접수 화면 옆 도우미 칸")에 "다 해줘". 같은 날 본인 확인·주문 확인 승인(운영자 RAG `backoffice/05` 제15조).
- 바꾸지 않는 것: 운영 도우미 질문·답(ADR-0036·0084 채팅 세션), 상담 접수(case-service `cs-intakes`) — 접수는 명령이 아니고 도우미도 아무것도 실행하지 않는다.

## 결정
1. **모양**: 상담 접수 화면(전화·채팅·메일 연락 남기기) 옆 칸. 상담원이 문의 종류를 고르면 도우미가 먼저 보여 준다. 질문을 쓰지 않아도 된다. 더 물을 것이 있으면 같은 칸에서 기존 질문 API(`POST /assistant/policy-questions`, 채팅 세션)를 쓴다.
2. **API**: `POST /api/v1/assistant/consult-guides`(ai-assistant-service, 계약 1.4.0).
   - 입력: 문의 종류 `category`(상담 접수와 같은 값 ORDER·DELIVERY·PAYMENT·REFUND·PRODUCT·ACCOUNT·OTHER), 연락한 번호로 회원이 조회됐는지 `memberFound`(선택), 화면이 보여 준 주문 상태 `orderStatus`(선택, 주문 서비스의 상태 값 그대로).
   - **개인정보·식별자를 보내지 않는다** — 고객 ID·주문 번호·전화번호·주소 없음. 주문 상태는 화면이 이미 조회한 값의 이름뿐이다.
   - 출력: ① 본인 확인(제15조 절 — 문의 종류에 맞는 줄을 고르는 것은 화면이, 본문은 문서에서) ② 그 종류·상태에 맞는 정책 근거 몇 개(문서 경로·절·발췌) ③ 활성 스냅숏.
3. **LLM 을 쓰지 않는다**: 근거는 검색만으로 고른다(설정 검색어 → 지금 스냅숏의 문서 조각, 임계값 그대로). 응답이 빠르고(모델 대기 없음) 문서에 없는 말을 만들지 않는다. 문서를 고치면(ADR-0092) 도우미 내용도 다음 색인부터 바뀐다.
   - 종류·상태별 검색어는 설정 `pmart.assistant.consult-guide`(설정 저장소)에 둔다 — 문서 구성이 바뀌면 설정만 고친다.
   - 본인 확인은 고정 검색어(설정 `identity-query`)로 1위 조각 하나.
4. **역할**(기본값 — 확인 필요): `CS_AGENT`·`OPERATOR_ADMIN`(상담 접수를 쓰는 역할). 그 밖 운영자 403.
5. **기록**: 도우미 요청은 저장하지 않는다(질문이 아니라 고른 값이라 다시 볼 일이 없다). 지표 `pmart.assistant.consult.guides{category,result}` 만.
6. **실패**: 활성 스냅숏이 없거나 임베딩 모델이 안 되면 503 — 화면은 도우미 칸에 "지금 안내를 불러오지 못했습니다"만 보이고 접수는 그대로 한다(접수를 막지 않는다).

## 결과
- 상담원은 연락을 받는 동안 질문을 쓰지 않고도 본인 확인 순서와 그 문의의 정책 근거를 본다.
- 화면: 요청서 `docs/handoff/clients/backoffice/2026-11-28-request-cs-consult-assistant.md`(접수 화면 옆 칸, 종류·회원 조회·주문 상태가 바뀔 때마다 다시 부름, 자유 질문은 같은 칸 아래).
- 남은 것: 주문 상태를 서비스가 직접 조회할지(지금은 화면 값), 상담 중 대화 내용 요약(하지 않음 — 녹취·대화 원문을 받지 않는다).
