# ADR-0070 화면 번호 규칙 — 사람이 보는 번호와 시스템 ID 를 나눈다

- 상태: 승인 (2026-11-18, 사용자). **배송·라이더 번호 모양은 ADR-0085(2026-11-22)가 대체** — 배송 `D74939255`(두 번째부터 `-2`), 라이더 `R4785`(목록엔 번호만)
- 근거(사용자 2026-11-18): "DLV-83649921-c0e3-… 이게 정확히 뭘 의미하는 번호인지 알 수 있어야 하지 않을까", "주문 100개면 뭐가 뭔지 저 긴걸 다 언제 확인해", "다른 쪽 시뮬레이션도 이렇게 직관적으로 보이게 다같이 적용되는 규칙을 정해야", "안에 들어가면 상세번호가 나오게" → 배송 "주문번호-순번", 라이더 "라이더 번호 6자리 + 가린 이름".
- 관련: 화면용 주문번호 8자리(2026-11-16 `docs/handoff/clients/all/2026-11-16-reply-display-order-number.md`), 포장 라벨 숫자 6자리(mfc-fulfillment F-5).

## 결정
1. **시스템 ID 는 그대로** 둔다(`ORD-…`·`DLV-…`·`RD-…` UUID — 서비스 사이 열쇠, 계약·이벤트·DB 키). 화면에 보일 **화면 번호를 따로** 둔다.
2. 화면 번호:

| 대상 | 화면 번호 | 예 | 정하는 곳 |
|---|---|---|---|
| 주문 | 숫자 8자리(무작위, 겹치지 않음) | `74939255` | order(있음) |
| 배송 | **화면용 주문번호-순번**(같은 주문의 몇 번째 배송, 1부터) | `74939255-1` 첫 배송, `74939255-2` 반납·회수·재발송 | dispatch 순번(`delivery_seq`, `DeliveryCreated.deliverySeq`) → execution·dispatch 응답 `deliveryNumber` |
| 라이더 | **숫자 6자리**(무작위, 겹치지 않음, 바뀌지 않음) + 가린 이름 | `김*수 · 482913` | rider(`riderNumber`, 가입 때) |
| 포장 | 라벨 숫자 4자리(2026-11-20 — 그 전 포장은 6자리) | `3051` | mfc-fulfillment(있음) |
| 직원 | 이름 · 사번 | `홍길동 · P2026-00001` | hr(사번 있음 — 2026-11-18 덧붙임). 운영자 ID(OP-…)는 처리자·결정자 칸에도 내지 않는다 |

3. **화면 규칙(모든 웹·앱·시뮬레이터 공통)**
   - 목록·표·지도·알림·대화에는 **화면 번호만**. 시스템 ID 를 목록에 내지 않는다.
   - 배송은 화면 번호 옆에 **종류 표시**(배송·재발송·다시 배송·반납·회수)를 붙인다 — 순번만으로는 무슨 배송인지 모른다.
   - 라이더는 **가린 이름 + 라이더 번호**. Google 계정(이메일)은 로그인 수단이라 화면에 내지 않는다. 전화번호는 상세에서만, 가린 값.
   - **상세 화면 안에 "시스템 번호" 칸**(접어 두고 복사 버튼) — 서버 로그·문의 대조용.
   - 찾기는 화면 번호로 된다(주문번호 — 배송 찾기 `orderNumber`, 라이더 번호 — `GET /riders?riderNumber=`). 배송 번호 `74939255-2` 로 찾으려면 앞 8자리로 주문을 찾고 순번으로 고른다.
   - 화면 번호를 아직 모르면(주문 확정 전, 옛 기록) 시스템 ID 끝 8자리를 회색으로 보이고 "번호 없음" 표시.
4. 순번은 dispatch 가 배송을 만들 때 주문마다 늘린다(DB 트리거 — 주문마다 잠금). 예전 배송은 생성순으로 채웠다(dispatch V13). 같은 주문의 회수·반납·재발송·다시 배송이 2, 3, … 이 된다.

## 결과
- 백엔드(PC 5, 2026-11-18): rider 0.12.0(V10 `rider_number`, 직원 목록·상세·찾기 `riderNumber`·`riderIds`, 본인 프로필, 운행 중 목록), tracking 0.10.0(관제 `riderNumber`), dispatch 0.10.0(V13 `delivery_seq`, `DeliveryCreated.deliverySeq`, 배정 이력 `deliveryNumber`), execution 0.26.0(V19, 배송 조회·직원 목록·내 배달 내역 `deliveryNumber`).
- 아직: 다른 응답에 라이더 번호를 직접 싣지는 않았다 — 배송 목록 등 `riderId` 만 있는 화면은 `GET /riders?riderIds=a,b,c`(50개)로 한 번에 붙인다. 관제 진행 중 배송에는 배송 번호가 없다(배송 상세에서).
- 클라이언트·시뮬레이터 알림: `docs/handoff/clients/all/2026-11-18-notice-display-numbers.md`, `docs/handoff/simulator/2026-11-18-notice-display-numbers.md`.

## 덧붙임 (2026-11-18)
- 직원 표시 = 이름 · 사번(인사 백오피스는 이미 사번). 승인함·처리 대기·조치 이력의 처리자 칸도 OP-… 대신. 운영자 ID 여럿을 이름·사번으로 한 번에 바꿀 HR 조회가 없으면 PC 1(HR)에 요청.

## 덧붙임 (2026-11-19) — 나머지 ID 까지 넓힘
백오피스 세션 요청(사용자 "겉에서는 관리자가 직관적으로 알아볼 수 있게, 들어가면 시스템 ID"). 사용자 결정: 접수·문의 = **날짜+일련번호**, 고객 = **가린 이름 · 고객번호 6자리**. 그 밖은 추천안 그대로.

| 대상 | 화면 표기 | 예 | 정하는 곳 |
|---|---|---|---|
| 접수 건(CASE-) | `C-MMDD-일련 4자리`(Asia/Seoul 날짜마다 1부터) | `C-1119-0042` | case(새로 — `caseNumber`) |
| 문의(INQ-, 고객·라이더) | `Q-MMDD-일련 4자리` | `Q-1119-0012` | case(새로 — `inquiryNumber`) |
| 고객(CU-) | 가린 이름 · **숫자 6자리**(무작위, 겹치지 않음, 바뀌지 않음 — 라이더와 같은 방식) | `김*수 · 482913` | customer(새로 — `customerNumber`, 가입 때·기존 고객 채우기) |
| 클레임(CLM-) | 주문번호 + 종류 + 그 주문의 몇 번째 클레임 | `74939255 반품 1`, `74939255 교환 1` | claim(새로 — 주문별 순번 `claimSeq` + 종류. 주문번호는 order) |
| 클레임 하위(환불 RFI- 등) | 주문번호 + 종류 + 순번 | `74939255 환불 1` | claim·payment(같은 방식, 주문별 순번) |
| 승인(AP-)·변경 요청(CR-)·결정(DC-) | 번호 없이 **종류 · 요청자 · 시각**(요청자는 직원 표기) | `가격 변경 · 홍길동 · 11/19 09:12` | approval(이미 있는 값 — 종류·요청자·시각) |
| 사가(SAGA-) | 주문번호 + 흐름 이름 | `74939255 재발송`, `74939255 취소` | orchestration(이미 있는 값) |
| 포장 인계(HOV-) | 포장 라벨 4자리(그 전 포장 6자리) | `3051 인계` | mfc(있음) |
| MFC 중지(STOP-)·출고·작업 지시 | 센터 + 종류 + 시각 | `부산진구지점 · 입고 중지 · 11/19 09:12` | mfc(이미 있는 값) |
| 후속 처리·행위 요청(AR- 등)·교대 인계(SH-·SHO-) | 그 일이 붙은 대상의 표기 + 종류 | `C-1119-0042 후속 1`, `11/19 오전 교대 인계` | case(접수 번호에 순번) |

공통 표시 규칙(모든 앱):
- **목록·표·링크 글자에는 화면 표기만** — 긴 시스템 ID 도, "ID 끝 8자리 회색"도 쓰지 않는다.
- **상세에는 "시스템 번호" 칸 + 복사 버튼**(지금처럼) — 장애 문의·로그 대조용.
- 찾기 칸은 화면 표기로 찾는다(번호 → 시스템 ID 는 서비스 조회, 예 `GET /riders?riderNumber=`·`GET /deliveries?orderNumber=`). 시스템 ID 를 붙여 넣어도 찾게 둔다.
- 화면 표기를 아직 못 받는 대상(번호를 매기기 전 옛 데이터·서비스 미배포)은 **종류 · 시각**으로 보이고 시스템 ID 는 상세에서만.
- 새 번호는 겹치지 않게 서비스 DB 가 정한다(유일 제약). 날짜+일련은 Asia/Seoul 날짜 기준, 한 날 9999 를 넘으면 5자리.

번호를 새로 매기는 서비스: case(접수·문의·후속), customer(고객번호), claim(주문별 순번). 각 서비스 요청서는 백오피스 세션(PC 2)이 나눠 쓴다 — case·bff 는 PC 2, customer·claim 은 각 주인(`docs/operations/pc-split.md`).

덧붙임(2026-11-20, mfc PC 3 — MFC 시뮬레이터 R-26, 사용자 "앞으로 발생하는 주문 인계 번호는 다 4자리로"): 포장 라벨 숫자는 새 포장부터 **4자리**, 같은 센터의 OPEN·SEALED 포장끼리 겹치지 않는다(인계·무효 뒤 다시 쓰임). 옛 6자리 포장은 그대로. 숫자 인계는 같은 라이더·배송 5번 틀리면 잠김(mfc-fulfillment 0.23.0).
