## {cipher} 제거 1·2단계 (사용자 "cipher를 없애려고 지금 vault 서버를 운용하려는건데")
- 방향 바로잡음: render.sh 가 Vault 를 읽고 {cipher} 를 남기는 안은 목적과 다름 → config-server 가 Git + Vault 복합 백엔드로 비밀을 Vault 에서 직접 읽고 pmart-config 의 {cipher} 를 없앤다.
- 1단계 `verify/verify-cipher.sh`: pmart-config(origin/main 4621365)의 {cipher} 79개(서로 다른 값 25)를 config-server 와 같은 EncryptorFactory 로 풀어 sha256 만 비교 — 75 일치, 4 불일치(auth 서명키 PEM 본문 형식, FCM 2개 한 줄 JSON 형식, customer signup-key-secret 은 {cipher} 에만 있음). 이관은 푼 값을 그대로 넣으므로 지장 없음. Firebase 출처 확인은 사용자 "확실히 필요없어".
- 추출기 고침: 여러 줄 따옴표 문자열(search-service query-instruction) 다음 줄을 키로 읽던 것, 목록 항목 번호([0]) 누락.
- **목록 주의**: Spring 은 목록을 우선순위 높은 출처 하나에서 통째로 받는다 → signing.keys[0] 는 private-key 와 kid 를 둘 다 Vault 에(kid 3개 같이 이관).
- 2단계 `verify/migrate-cipher.sh` + setup 확장: KV v2 `config/`, 정책 `config-server-read`, AppRole `config-server`(1h·최대 24h), 관리자 정책에 config/·sys/mounts/config·sys/audit/* 추가(root 없이 관리자만으로 setup 되게). 시험(옛 정책·root 폐기·관리자 토큰만)에서 감사 로그 권한 부족을 찾아 고침.
- pc2 실제: 사용자가 관리자 토큰으로 실행 — 44경로·82필드({cipher} 79 + kid 3) sha256 모두 일치. 서비스 동작은 아직 그대로(config-server 연결은 3단계).

## {cipher} 제거 3단계 — 서비스가 Vault 에서 직접 읽기(Spring Cloud Vault)
- 사용자 결정: config-server 복합 백엔드(학습 프로젝트 방식)는 정석이 아님 → **서비스마다 Spring Cloud Vault 로 자기 비밀만** 읽는다(최소 권한, 운영 Kubernetes 인증과 같은 구조). 2단계 데이터(`config/<앱>,lan`)는 profile-separator `,` 로 그대로 쓴다. TLS 는 처음부터(사용자 "이왕하는거면 tls 바로").
- 3-1: `spring-cloud-starter-vault-config`(Spring Cloud BOM) — libs.versions.toml, pmart.spring-service·pmart.spring-gateway.
- 기본 꺼짐: `common-observability` 에 `VaultDefaultsPostProcessor`(spring.cloud.vault.enabled=false, 가장 낮은 우선순위). **서비스 application.yml 49개는 고치지 않는다** — vault:// import 는 설정 데이터 단계(후처리보다 먼저)라 yml 에 두면 로컬도 Vault 에 붙으므로, import 는 LAN 컨테이너 환경변수(SPRING_CONFIG_IMPORT=optional:configserver:,vault://)로만 준다. 단위 시험 4개 통과.
- 3-4: `VaultClientLanIT`(Testcontainers Vault 1.21.4 dev-tls) 3개 통과 — 환경변수 이름 그대로(SPRING_CLOUD_VAULT_APPROLE_ROLEID·KV_PROFILESEPARATOR·SSL_TRUSTSTORE(TYPE=PEM) 등), AppRole+TLS(CA PEM), Vault 가 Git 을 이김, 다른 서비스 경로는 정책으로 막힘, Vault 에 private-key 만 두면 kid 가 사라짐(목록 통째 교체 — kid 도 이관한 근거), 환경변수 없으면 Vault 없이 기동. 고친 것: -dev-tls-cert-dir 는 있는 폴더여야 함.
  - ⚠ 이 시험 시작 때 실메모리 3.6GB(규칙 4GB) — 측정과 실행을 한 명령에 묶어 멈추지 못했다. 이후 측정 먼저.
- pc2 인증서: PC 1 백엔드 세션이 `lan.sh tls-issue pc2`(SAN IP:192.168.0.34·DNS:ds603-12, 2027-11-28 만료) → 사용자 승인 후 scp, sha256 일치. pc2 Vault 를 TLS 모드(0.0.0.0:8200, api_addr https://192.168.0.34:8200)로 재시작 — LAN 주소로 사설 CA 검증 통과(sealed 503). unseal 은 사용자.
- 미룸: 서비스 영향 시험(실메모리 3.4GB < 4GB).
- 3-3 `service-roles.sh`: placement.conf 의 Spring 앱 50개(pc2 16·pc3 14·pc4 10·pc5 10)마다 정책 `svc-<앱>`(config/data/<앱>·<앱>,* 읽기만) + AppRole `svc-<앱>`(1h·최대 24h, secret_id·token 을 그 PC IP/32 로 묶음). 정책 `pmart-deployer`(render.sh 용 — role-id 읽기·secret-id 발급만, 비밀·역할 설정 못 바꿈).
  - 시험에서 확인: Vault PC(pc2)의 컨테이너는 Vault 에 **172.21.0.1(Docker 게이트웨이)** 로 보인다 → pc2 앱만 Docker 대역(172.16.0.0/12, 192.168.65.0/24)도 허용. 스크립트가 끝에 이 PC 컨테이너에서 임시 secret-id 로 TLS 로그인해 보고 폐기한다.
  - placement.conf 줄 끝 `\` 잇기: 정규식 대신 줄 단위로(Windows 셸에서 정규식 이스케이프가 깨짐).
- `vault.sh deployer-token`: PC 1 render.sh 용 배포 토큰(pmart-deployer, -orphan, period 768h)을 .init/ 파일로만 만든다(시험: secret-id 발급 OK). pc2 방화벽은 기존 규칙 "PMart Docker published ports (LAN)"(Docker 백엔드, 192.168.0.0/24, 모든 포트)로 8200 허용 확인.
