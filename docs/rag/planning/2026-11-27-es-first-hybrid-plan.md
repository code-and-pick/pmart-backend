## 0. 목표

1. 답이 문서 카드·정해진 문장으로 충분한 요청은 **LLM 없이**(필요하면 임베딩도 없이) 끝낸다.
2. 키워드로 놓친 후보는 벡터 검색으로 보강한다.
3. 비교·설명·절차 조합이 필요할 때만 검증된 근거로 생성한다.
4. 각 종료 지점의 판정 기준을 **측정으로** 정한다(지금 RAG 에서 측정된 문제 — 옳은 답 거절, 관계없는 발췌 — 를 되풀이하지 않게).

| 공개 정책·FAQ(고객) | `docs/rag/rag-docs/customer_app` + 고객 RAG DB 의 스냅숏·문서 상태 | **ES 고객 RAG 색인**(새로) | 고객 RAG pgvector | — |
| 내부 매뉴얼·규정(직원) | `docs/rag/rag-docs` 전체 + 운영자 RAG DB 의 스냅숏·문서 상태 | **ES 운영자 RAG 색인**(새로) | 운영자 RAG pgvector | — |
| 주문·배송·결제 | 각 업무 서비스 | — | — | 업무 API(지금처럼 고객 `ORDER_STATUS` 는 order-service 조회) |

- 고객 색인과 운영자 색인은 나눈다(지금 DB 를 나눈 것과 같은 이유 — 내부 문서가 고객 검색에 나오지 않게).
- 우리 문서의 원본은 백오피스 화면이 아니라 **git 의 `rag-docs`** 다(PR → 병합 → PC 1 재색인). 백오피스에서 매뉴얼을 직접 고치는 화면이 생기기 전까지는 Outbox·CDC 대신 지금의 색인 작업(`ingestKnowledge`, `lan.sh rag-ingest`)을 시작점으로 쓴다.
- 문서마다 상태(발행·개정·폐기)를 원본 쪽에 둔다 — 지금은 스냅숏 단위 기록만 있고 문서별 상태가 없다(11-20 확인). RAG DB 에 문서 상태 표를 더한다.

### 1-2. 적재 순서 — ES 선 색인 → 임베딩 → pgvector 후 적재

받은 글의 4단계를 우리 구조에 맞춘 것:

| 단계 | 하는 일 | 우리 구현 위치 | 완료되면 |
|---|---|---|---|
| 1. 원본 확정 | manifest·파일 해시·커밋·문서 상태를 기록하고 새 스냅숏(BUILDING) | `KnowledgeIngestor`(지금 있음) | — |
| 2. 청킹 → ES 적재 | `MarkdownChunker` 로 **한 번만** 청킹, 1 청크 = 1 ES 문서(`chunkId`·`documentId`·`snapshotId`·`accessScope`·`authority`·`contentHash`·`status`·제목 경로·본문), 스냅숏별 색인에 bulk | 같은 작업의 새 단계 | 키워드 검색 준비(아직 별칭 전환 전) |
| 3. ES → 임베딩 | 스냅숏 색인의 문서를 읽어, `contentHash` 가 `embedding_cache` 에 있으면 건너뛰고 없을 때만 Qwen3 임베딩 | 임베딩 단계(지금 캐시 재사용) | — |
| 4. pgvector 적재 | 벡터 + ES 에서 읽은 청크 본문·메타데이터를 `doc_chunk` 에 넣음 | 지금 있음 | 벡터 검색 준비 |
| 5. 활성화 | 건수·해시 검증 뒤 **DB 스냅숏 ACTIVE 전환과 ES 별칭 전환을 함께** | `SnapshotStore.activate` + 별칭 | 두 검색이 같은 스냅숏을 본다 |

이 순서를 쓰는 이유(받은 글)와 우리 조건:

- **청킹 한 번**: 키워드 단위와 벡터 단위가 같다. 우리는 이미 청킹이 하나(`MarkdownChunker`)라 같은 효과이며, ES 문서와 `doc_chunk` 가 같은 `chunkId` 를 갖게 한다.
- **임베딩이 느려도 키워드 검색은 먼저**: 임베딩은 PC 2 Ollama(CPU)를 상품 의미 검색과 함께 쓴다 — 전체 임베딩 642청크 652초(11-27 실측). 다만 우리는 **스냅숏 단위로 한꺼번에 전환**하므로, 별칭을 먼저 바꾸면 ES 와 pgvector 가 다른 스냅숏을 보게 된다. 그래서 "키워드 먼저"는 **새 스냅숏이 아니라 지난 ACTIVE 스냅숏이 계속 검색되는 것**으로 얻는다(색인 중에도 기존 검색은 그대로 — 지금도 같은 성질).
- **실패 다시 하기**: 임베딩·pgvector 적재가 실패하면 그 스냅숏 색인의 문서 ID 로 다시 읽어 이어서 한다. 스냅숏이 끝내 실패하면 BUILDING → FAILED 이고, ES 쪽 스냅숏 색인도 함께 지운다(11-27 #553 의 정리 규칙과 같게).
- **지킬 것 — 정본은 ES 가 아니다**: 3단계는 ES 를 "정제된 말뭉치"로 읽지만, 버전 확인(어느 스냅숏·문서 상태가 맞는지)은 RAG DB 의 원본 기록으로 한다. ES 색인은 언제든 원본에서 다시 만들 수 있어야 한다.

### 1-3. 폐기·비활성 전파

- 문서를 폐기하면 원본 상태 변경 → ES 문서 `status` 갱신 → pgvector `is_active = false`. **본문이 바뀌지 않으므로 임베딩을 거치지 않는다**(임베딩 대기열 뒤에 밀려 늦게 내려가는 일이 없게).
- 스냅숏 재색인으로 문서를 뺀 경우는 활성화(DB + 별칭 동시 전환) 한 번으로 양쪽에서 함께 내려간다.
- 마지막 방어선: 검색 결과를 쓰기 전에 그 청크의 스냅숏이 지금 ACTIVE 인지, 문서 상태가 유효한지 확인하고 아니면 버린다(구성의 "조회 시점에 확인").

## 2. 검색 요청

### 2-1. 흐름 (두 서비스 같은 코드)

```
질문
 → [앞단, 지금 있음] 요청 제한(고객) · 질문 분류(실행 요청·실시간 조회) · 주문 상태(고객) · 상품 질문(search-service)
 → [의도] 찾기 / 단순 확인 / 설명·비교·절차 조합
 → ES 키워드 + 필수 조건(권한 범위·ACTIVE 스냅숏·문서 상태)
 → 충족됐나? ─ 예 → ① ES 에서 종료
             └ 아니요(후보 부족·설명 필요) → 질문 임베딩 → pgvector → ES 후보와 병합 → 검증
                   → 찾기면 ② 벡터 검색으로 종료
                   → 설명·조합이고 근거 충분 → ③ 생성
                   → 그 밖 → 결과 없음 · 조건 확인 · 담당 안내
```

### 2-2. 종료 지점

| 종료 | 언제 | 돌려주는 것 | 모델 호출 | 고객 예 | 직원 예 |
|---|---|---|---|---|---|
| 앞단(지금 있음) | 실행 요청·실시간 조회·주문·상품 | 정해진 문장·상품 카드 | 없음 | "무가당 두유 1L" → 상품 카드 | "ORD-… 지금 어디야?" → 조회 화면 안내 |
| **① ES** | 찾기 의도이고 ES 상위 결과가 기준을 넘을 때 / (고객) 승인 FAQ 와 거의 같을 때 | 문서 카드(제목·조·경로) / 승인 FAQ 답 | 없음(임베딩도 없음) | "반품 기간 FAQ 보여줘" → FAQ 답 | "오배송 매뉴얼 찾아줘" → 매뉴얼 카드 |
| **② 벡터** | 찾기 의도인데 ES 후보가 부족할 때 | 병합·검증한 문서 카드 | 임베딩 1회 | "포장 뜯긴 채 왔을 때 안내" → 관련 정책 카드 | "고객이 다른 상품을 받았을 때 쓰는 문서" → 오배송 매뉴얼 카드 |
| **③ 생성** | 설명·비교·절차 조합이고 근거가 충분할 때 | 고객 답 / **직원용 초안**(근거 첨부) | 임베딩 1회 + 생성 1~2회 | "쿠폰 주문을 부분 취소하면 쿠폰·배송비는?" | "오배송인데 일부는 받겠대요, 어떻게 처리해요?" |
| 그 밖 | 필수 조건 미충족·근거 부족 | 결과 없음 · 조건 확인 · 담당 부서 안내 | — | 고객센터 문의 버튼(지금 있음) | 담당 부서 안내 |

- 찾기 의도의 문서 카드는 지금 없는 답 종류다(새 `answerMode`, 계약 변경, 백오피스·고객앱 화면).
- 고객 "승인 FAQ 바로 답"은 2026-11-20 사용자 결정("FAQ 는 목록 화면 전용")을 바꾸는 일이라 따로 결정이 필요하다.

### 2-3. 판정 기준 (계획의 핵심)

- **① 충족 판정**: BM25 점수는 상한이 없어 기준값 하나로 정하기 어렵다. 후보: 상위 1위와 2위의 차이, 질문 낱말이 제목 경로에 있는지, 필수 조건 일치 — 평가셋으로 정한다.
- **② 병합**: 순위는 앱에서 RRF(ES Basic 은 내장 RRF 가 403 — 11-18 실측)로 합치되, **근거 있음·없음은 코사인 절대값으로 따로 판정**한다(RRF 점수에는 절대 의미가 없다). 지금 임계값 0.425·발췌 하한 0.45 는 혼합 점수 기준이라 다시 맞춘다.
- **③ 검증**: 지금의 인용 검사·고객 추가 검사·다시 생성을 그대로 쓴다. 11-27 측정의 문제(부정 검사 잘못 거절, 관계없는 발췌 N01)를 P1 에서 먼저 고친다.
- **의도 분류**: 처음은 규칙(지금 `QuestionClassifier` 처럼)으로 하고 평가셋 라벨로 정확도를 잰다.

## 3. 부하 — 받은 글의 주장과 우리 숫자

| 받은 글 | 우리 상황(측정·설정) | 계획에서 |
|---|---|---|
| "모든 질문이 임베딩 + 생성을 거친다" | 맞다 — 앞단(분류·상품·주문)을 지나면 모든 문서 질문이 임베딩 1회 + 생성 1~2회 | ①에서 끝나는 만큼 임베딩·생성이 줄어든다 |
| "임베딩·생성 모두 GPU" | 임베딩은 **CPU**(`num_gpu 0`), 생성만 GPU. 둘 다 PC 2 한 대를 상품 의미 검색(질문 임베딩 제한 1.5초)·꼬리표 생성과 함께 쓴다 | 절감 효과는 GPU 보다 **PC 2 공유 자원 다툼**이 줄어드는 데서 크다 |
| "Thinking 토큰이 길다" | 지금은 **생각 끔**(`disable-thinking: true`). 생성 한 번 0.8~3.0초, LAN 응답 중앙 1.7초·최대 9.7초(11-27) | 생각을 켜는 것은 P5 실험으로만 |
| "상담원 검색의 70~80% 가 단순 조회", "GPU 70% 절감", "0.05초 응답" | **우리 측정이 아니다.** 우리 질문 분포는 재 본 적이 없다 | P1 에서 우리 질문 유형 분포를 재고, 그 숫자로 효과를 말한다 |

## 4. 생성 부하를 더 줄이는 것 (받은 글의 두 가지)

### 4-1. 시맨틱 캐시

- 자주 묻는 복합 질문의 **검증 통과한 생성 답**을 캐시하고, 비슷한 질문이면 생성 없이 돌려준다.
- 조건(지키지 않으면 틀린 답을 빠르게 내보낸다):
  - 키에 **스냅숏 ID·접근 범위**를 넣고, 스냅숏이 바뀌면 전부 버린다(정책이 바뀌었는데 옛 답이 나가지 않게).
  - 인용 검사를 통과한 `GENERATIVE` 답만. 발췌·근거 없음은 넣지 않는다.
  - 주문·금액처럼 업무 API 값이 들어간 답은 넣지 않는다.
  - 고객·직원 캐시를 나눈다. 질문 원문을 저장하지 않는 고객 쪽(C5)은 질문 벡터와 답만 둔다.
  - 비슷함 기준은 높게 두고 평가셋으로 잰다 — 다른 질문을 같은 질문으로 보면 틀린 답이 나간다(예: "부분 취소"와 "전체 취소").
- 저장: 같은 RAG DB 의 pgvector 표. RAG 서비스는 지금 Redis 를 쓰지 않으므로 Redis 를 새로 들이지 않는다.

### 4-2. 추론 깊이 제어

- 생각 모드를 켤 때만 해당한다. 근거 1~2개인 단순 요약은 생각 끔, 여러 규정이 충돌하는 복합 건만 생각 켬으로 나눈다.
- 확인할 것: Ollama 에서 생각 토큰 길이를 직접 제한하는 옵션이 있는지. 전체 출력 길이(`num_predict`)로 자르면 JSON 답이 중간에 잘릴 수 있다. 처리 제한(Ollama 25초, 다시 생성 포함)에 들어가는지도 잰다.

## 7. 위험

- **잘못 끝냄**: ①·②에서 관계없는 카드로 끝내면 LLM 보다 빠르게 틀린 답을 낸다 — 종료 지점마다 평가셋과 기록이 먼저다(P1).
- **두 저장소 어긋남**: ES 와 pgvector 가 다른 스냅숏을 보면 키워드 결과와 벡터 결과가 서로 다른 정책을 가리킨다 — 활성화 동시 전환과 조회 시점 확인으로 막는다.
- **공유 자원**: PC 2 Ollama 는 RAG·상품 의미 검색·꼬리표 생성이 함께 쓴다. 실험·재색인마다 PC 1 에 알린다.
- **숫자 없는 기대**: 부하 절감 폭은 우리 질문 분포를 재기 전에는 말하지 않는다.

## 8. 사용자 결정 (2026-11-27, P0)

- **D1 승인 — ES-First**: RAG 는 ES BM25 키워드 검색을 먼저 하고, 결과가 부족하면 지금의 PostgreSQL + pgvector 벡터 검색을 한다.
  - **적용하지 않는 것**: 앞서 논의한 "ES 가 BM25 와 벡터 검색을 모두 맡는" 구조(PR #558 리뷰 대상) — 벡터는 pgvector 에 그대로 둔다.
  - 상품 검색은 ADR-0088 그대로. 운영자 RAG(ai-assistant-service)·고객 RAG(customer-assistant-service) 서비스 분리 그대로.
  - P3 에서 지금 검색과 비교 검증 → 효과가 확인되면 **새 ADR** 을 쓴 뒤 P4 운영 적용. **P3 에서 개선 효과가 없으면 P4 보류.**
- **D2 조건부 승인 — 고객 승인 FAQ 바로 답**: 고객 질문이 지금 유효한 승인 FAQ 와 **명확히** 일치하면 LLM 없이 그 FAQ 답을 그대로 돌려준다.
  질문의 조건·맥락이 다르거나 복합 설명이 필요하면 지금의 RAG 검색·생성으로. 근거가 부족하면 FAQ 답을 억지로 돌려주지 않는다.
- 순서: P1 부터. **검색 종료 판정 기준과 답변 검증 문제를 먼저 측정하고 개선**한다.

### ① 종료 지점 기록 — 구현(브랜치 `rag/p1-exit-metrics`, 아직 LAN 아님)
- 두 서비스 `AnswerGenerator.Generated` 에 `exit`(문서 경로가 끝난 곳)·`attempts`(생성 시도마다 결과)·`topSimilarity`(1위 근거 혼합 유사도)를 싣고, `AnswerMetrics` 가 Prometheus 지표로 센다. 질문 원문·답·본문은 싣지 않는다.
  - `pmart_assistant_answers_total{exit}` / 고객 `pmart_customer_assistant_answers_total{exit}`: 앞단(REALTIME_DATA_REQUIRED·OUT_OF_SCOPE·(고객) ORDER_STATUS·PRODUCT_INFO·(고객) BLOCKED_WORDS),
