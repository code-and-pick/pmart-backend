# 칠곡 CDC 묶음 피킹(2단계) 설계 — 초안

- 작성: cdc 세션, 2026-11-25. 사용자 "이거 설계 시작해"(시뮬레이터 R-18 2단계).
- 상태: **설계 확정(사용자 결정 2026-11-25, §7)** — 다음은 계약(cdc-location·cdc-outbound) → 구현. 구현 전이다.
- 대상 서비스: cdc-outbound(주), cdc-location(방식 속성 — §7 결정 3 에 따라). cdc-inventory 는 바꾸지 않는다(§4).

## 1. 왜

1단계(시뮬레이터 99ad207)는 계약을 바꾸지 않으려고 피킹을 TRF(= MFC 하나) × 구역 × 층 작업으로 두었다. 그래서 한 SKU 를 여러 MFC 몫만큼 **한 번에** 집는 현장 방식은 화면에서만 흉내 낸다.

현장 근거(`docs/simulator/cdc/chilgok-dc.md` §2 — 사용자 "절대 거스르지 말 것")를 보면 일하는 방식이 다르다.
- **FC**: 지역 바코드 → 지역 카트에 담는다(한 지역 = MFC 여럿).
- **분배**: 지역 카트의 야채 → PDA 에 지역·MFC 별 수량이 뜬다 → MFC 크레이트에 담는다 → 지역 바코드를 찍는다.
- **라인(DAS)**: 자키가 상품 박스를 가져온다 → 스캔 → 작업자 색 불이 켜진 MFC 칸마다 숫자만큼 담는다.

## 2. 업무 근거(바꾸지 않는 것)

`docs/business/WMS-business-logic.md`:
- **CDC-F-017**: Wave 는 여러 이관행을 묶을 수 있다. "합산 집품 후 분류를 하더라도 원이관 목적을 잃지 않는다." 작업행은 SKU·LOT·원천 위치별이고, 합산 집품이면 **원요청행별 배분 근거를 잃지 않는다.**
- **같은 곳의 예**: 원이관 A36·B24 를 합산 60 으로 집었으면 분류도 A36·B24 로 설명돼야 한다. 분류가 A36·B20 = 56 이면 **4 는 미설명**이다. 영향받는 검품·상차·출발을 보류하고, 60 을 56 으로 덮거나 4 를 손실로 지우지 않는다.
- **정책 17.2-4**: 여러 TRF 를 묶어도 원행·예약·목적 LPN·확정량을 섞지 않는다. 한 TRF 를 여러 Task 로 작업해도 여러 출발을 허용하는 것은 아니다.
- **CDC-F-017**: SKU 분류 문자열만으로 작업자·분류 목적지를 자동으로 정하지 않는다.
- **정책 17.4**: 피킹·검품·상차는 CDC 총현물을 줄이지 않는다. 실제 출발 때만 줄인다.
- **CDC-F-009**: FEFO·안전량·기존 예약이 동선 효율보다 앞선다.

## 3. 모양(제안)

### 3.1 피킹 방식 — 구역·선반 통로가 정한다

| 층·구역 | 방식 | 묶음 | 집는 그릇 | 나눠 담기 |
|---|---|---|---|---|
| 5F A 냉동 | DPS | 없음 — TRF 하나 | MFC 박스(빈 박스가 DPS 로 옴) | 없음(피킹 = 분류) |
| 5F C·D | 박스 피킹 | **지역**(같은 지역의 TRF) | 지역 카트 | 출고대기에서 MFC 롤테이너로 |
| 5F E·F, 7F G·H | FC | **지역** | 지역 카트 | 출고대기에서 MFC 박스로 |
| 6F B 야채 | 분배 | **지역** | 지역 카트 | 분배대에서 MFC 크레이트로 |
| 6F B 그 밖 | 라인(DAS) | **SKU — Wave 안 모든 MFC** | 상품 박스(자키) | 라인 칸(MFC 박스)으로 |

- 방식은 **상품 분류 글자가 아니라 위치(구역·선반 통로)의 설정값**으로 정한다(F-017).
- 6층 야채 선반 통로와 그 밖 선반 통로를 나누는 설정이 필요하다 → §7 결정 3.
- 지역 = PDA 지역 바코드 단위다. 지금은 4지역(부산권 BJG·BNG / 호남권 MOKPO / 충청권 SEJ / 강원권 CHC, chilgok-dc.md CDC-6)이다. 지역 ↔ MFC 대응표는 cdc-outbound 가 갖는다(시뮬레이터 설계 §7 "대응표는 cdc-outbound").

### 3.2 Wave 릴리스 — 묶음 작업 만들기

지금(0.3.0)은 TRF × 구역 × 층마다 PICK Task 하나다(`domain/PickPlan`). 바꾸는 것:
1. 할당의 지금 LOT·위치를 읽는다. 지금과 같다.
2. 줄마다 방식을 정한다(위치 → 방식 설정).
3. 묶음 열쇠로 나눈다.
   - DPS: (TRF, 구역, 층)
   - 지역 묶음: (지역, 방식, 구역, 층)
   - 라인: (방식, 구역, 층)
4. 같은 (SKU, LOT, 위치)는 한 작업 줄로 합친다. 그 줄 밑에 **TRF 별 몫**(`task_line_share`: trfId·mfcId·plannedQty)을 남긴다. 이것이 F-017 의 "원요청행별 배분 근거"다.
5. Task 에 `pickMode`(DISCRETE·REGION_BATCH·SKU_BATCH)와 `regionCode` 를 둔다. 한 묶음 작업이 너무 크면 줄 수로 자른다(크기 = §7 결정 4).

### 3.3 피킹 실적 — 줄 합계로 받고 TRF 몫으로 나눈다

- PDA 는 지금처럼 줄(SKU·LOT·위치)마다 pickedQty·shortQty 합계를 보낸다(`pick-results` 모양 그대로).
- 줄이 끝나면(피킹 + 부족 = 계획) 실피킹을 **TRF 몫에 나눈다**. 부족이 있으면 누구 몫을 줄일지 규칙이 필요하다 → §7 결정 2.
- 나눈 결과로 `transfer_line.picked_qty·short_qty` 를 TRF 마다 더한다. 지금처럼 TRF 가 PICKED 가 되는 조건과 `PickShortageReported` 가 이어진다.

### 3.4 나눠 담기 — 지금 분류 실적을 그대로 쓴다

- 라인 칸·분배 크레이트·출고대기 MFC 롤테이너에 담은 결과 = TRF 의 BOX 구성이다. 지금 `/sorting-results`(BOX 하나 = TRF 하나, 분류 ≤ 실피킹)를 그대로 쓴다. **새 경로가 필요 없다.**
- 라인 불·숫자 = TRF 몫의 실피킹이다. Task 응답의 줄 밑 `shares[]` 로 보인다. 시뮬레이터·PDA 는 이 숫자를 켠다.
- 미설명 수량(몫의 실피킹 − 분류)은 지금 출발 준비 조회의 `UNSORTED_QTY` 로 보인다. F-017 은 이때 "영향 출발 보류"를 요구한다. 지금 출발 검증은 실린 BOX 만 대조하므로, 미설명이 있는 TRF 의 출발 검증을 막을지 정해야 한다 → §7 결정 5.

## 4. 재고(cdc-inventory) — 바꾸지 않는다

- 시뮬레이터 2단계 제안은 "라인 버퍼 위치로 MOV(예약 함께)"였다.
- 이 설계는 **MOV 하지 않는다**. 지금 단건 피킹도 집은 물건을 출발 때까지 원위치 장부에 둔다(정책 17.4 — 피킹은 현물을 바꾸지 않음). 묶음만 MOV 하면 같은 물건의 장부 위치 규칙이 둘이 된다.
- 할당·예약은 TRF 마다 그대로다. 출발 TOUT·잔여 해제도 그대로다.
- 집은 물건의 현재 귀속(카트·라인·칸)은 cdc-outbound 의 작업·LPN 기록이 추적한다(F-017 "원피킹 실물은 미분류·분류완료… 현재 귀속을 추적").
- 버퍼 칸 장부가 필요하다고 정하면(§7 결정 6) 그때 cdc-location 에 버퍼 칸(통로 93~, CDC-5)과 MOV 를 더한다.

## 5. 계약 변화(예상, 결정 뒤 확정)

- cdc-outbound
  - `Task`: `pickMode`·`regionCode` 추가
  - `Task.lines[].shares[]`: trfId·mfcId·plannedQty·pickedQty·shortQty 추가
  - `Task.trfId`: 묶음이면 비움(또는 `trfIds[]`)
  - 다음 작업 받기 거르기에 `pickMode` 추가
  - 지역 대응표 조회(내부 또는 공개 — 시뮬레이터·PDA 지역 바코드용)
  - 모두 필드를 더하는 하위 호환이다. 단, `trfId` 를 비우는 것은 소비자(시뮬레이터) 확인이 필요하다.
- cdc-location(결정 3 이 "위치 속성"이면): 선반 통로·위치에 `pickMethod` 설정값 추가 → 일괄 조회 응답에 포함.
- 사건: `PickShortageReported` 는 TRF 마다(지금과 같은 모양) 낸다.

## 6. 하지 않는 것

- 설비 제어(DAS 불 켜기·컨베이어)는 하지 않는다 — 가상 설비, 결과만 받는다(WMS §0.6).
- MFC 고객 주문 피킹과 섞지 않는다(F-017).
- 한 TRF 를 여러 출발로 나누지 않는다.
- 피킹 뒤 취소는 하지 않는다(사용자 확정 2026-11-25).

## 7. 결정 (사용자 2026-11-25)

| # | 질문 | 결정 |
|---|---|---|
| 1 | 묶음 범위 | **§3.1 표대로** — DPS 는 TRF 하나, 박스·FC·분배 = 지역 묶음, 라인 = SKU 묶음(Wave 안 모든 MFC) |
| 2 | 묶음 피킹 부족을 누구 몫에서 뺄지 | **TRF 기한(dueAt) 이른 것부터 채운다** — 남은 부족은 기한이 늦은 TRF 몫에서(기한이 같으면 trfId 순으로 뒤쪽에서) |
| 3 | 6층 야채(분배)·그 밖(라인)을 가르는 것 | **선반 통로 설정값** — cdc-location 위치에 `pickMethod`, 상품 분류 글자로 가르지 않는다(F-017) |
| 4 | 미설명 수량(몫의 실피킹 − 분류)이 있으면 | **그 TRF 출발 검증을 막는다**(F-017 "영향 출발 보류") — 단건 피킹에도 같이 적용 |

백엔드 판단(사용자에게 알림, 반대하면 바꾼다):
- 묶음 작업 하나의 크기(줄 수·지역 카트 최대 TRF 수)는 설정값으로 두고 기본값을 두지 않는다. 설정이 없으면 자르지 않는다.
- 라인 버퍼를 재고 장부 위치로 두지 않는다(MOV 없음, §4).
