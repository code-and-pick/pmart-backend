# AI 추천 배차 성능 검증 — RouteFinder vs OR-Tools (2026-11-13, PC 5)

ADR-0058 결정 11 "OR-Tools 결과와 비교해 검증한다"(원문 Delivery §2.1 ③ "성능 검증")의 첫 결과.

## 방법
- 도구: `ai-services/delivery-dispatch-optimizer/tools/evaluate.py` (`uv run python tools/evaluate.py --instances 60 --seed <n>`).
- 문제: MFC(강남역 부근) 둘레 약 ±2.8km 에 알뜰배달 4~12건, 라이더 (배송/4)~(배송/2)명(라이더 → MFC 60~900초), 출하 대기 0~600초, 묶음 최대 3건·지연 한도 20분·늦음 가중 2.
- 도로 시간: **합성값**(직선거리 × 1.3 ÷ 5m/s). 실제 카카오 도로 시간이 아니다.
- RouteFinder: 서버 그대로(`planner.plan` + RouteFinder rf-transformer-100, 지연 한도를 시간창으로 넣음).
- OR-Tools: dispatch Java 계산과 같은 방식(알뜰배달 1~3건 후보 + 방문 순서 순열 + 지연 한도, CP-SAT 라이더 ↔ 묶음, 2초).
- 둘 다 같은 비용식(dispatch `BundleProblem`)으로 잰다.

## 결과
| | seed 1 | seed 2 |
|---|---|---|
| 배정한 배송 합계 (RouteFinder / OR-Tools) | 347 / 448 (−23%) | 324 / 413 (−22%) |
| RouteFinder 가 덜 배정한 문제 / 더 배정한 문제 | 51 / 0 | 46 / 0 |

| 2건 이상 묶음 수 | 131 / 159 | 123 / 151 |

(시간창 없이 돌린 seed 1 첫 결과도 347 / 448, +26.2% 로 거의 같았다.)

## 해석
- **지금 연결 방식의 RouteFinder 는 OR-Tools 보다 분명히 못하다** — 배송을 20% 넘게 덜 배정하고, 같은 수를 배정해도 비용이 20~30% 높다. 계산 시간은 비슷하다.
- 이유(추정): RouteFinder 는 **차량 수 제한이 없는** VRP 로 학습됐다. 고객을 3건씩 채우지 않고 짧은 경로를 여럿 만든다(묶음 수가 OR-Tools 보다 적다). 우리 문제는 라이더 수가 정해져 있고 라이더마다 MFC 까지 오는 비용이 다르다 — 경로가 라이더보다 많으면 남는 배송이 생긴다. 라이더 짝짓기는 모델 밖(서버 규칙)이라 이 차이를 메우지 못한다.
- 원문 §2.1 ③ "모델별 입력 형식과 문제 환경을 맞추고, 필요하면 추가 학습 후 성능 검증"의 "추가 학습"이 필요한 상태다.

## 다음 후보(결정 필요)
1. LAN 에서 AI 를 **끄고** OR-Tools 로 운영하다가, 추가 학습으로 OR-Tools 를 넘으면 켠다(추천 — `pmart.dispatch.ai.base-url` 을 비워 두면 된다).
2. 원문대로 지금 켠다 — 배정이 덜 되면 배송이 다음 판단·재요청으로 밀린다(배차 지연).
3. 추가 학습(fine-tuning): 우리 문제 모양(라이더 수 제한·라이더별 출발 비용·최대 3건·20분 한도)으로 RouteFinder 를 다시 학습 — PC 5 GPU(RTX 2060 6GB, ollama 와 나눠 씀). 학습 데이터 생성기·평가는 이 도구를 늘려 쓴다.
4. GreedRL 비교(원문 후보 — 픽업·배송 문제를 직접 다룬다).

## 추가 학습 결과 (2026-11-13 저녁, PC 5 — 사용자 "추가학습해")
- 도구: `ai-services/delivery-dispatch-optimizer/tools/finetune.py`. **보상만 바꿨다**: 공개 가중치는 열린 경로 길이 합을 줄이도록 배워 1건 경로를 많이 만든다 → 비용 = Σ고객 도착(MFC 출발부터) + λ × 경로 수(경로 = 라이더 한 명). 문제는 서버 추론과 같은 방식(평가 도구 분포, `_normalize`, `planner._deadlines` 시간창, 용량 1/3, 열린 경로). POMO 다중 시작 REINFORCE(같은 문제 평균 기준선), 공개 가중치에서 시작, Adam 1e-5, 배치 64, 3000 단계, **CPU 4스레드 약 17분**(GPU·ollama 안 씀). 검증(고정 문제 126개 탐욕 디코딩)이 가장 좋았던 가중치를 저장.
- 학습 문제 seed 7·검증 1234, 아래 평가는 seed 1·2(처음 검증과 같은 문제).

| 배정 배송 합계 seed 1 (RouteFinder / OR-Tools 448) | 347 (−23%) | 425 (−5%) | **439 (−2%)** |
| 배정 배송 합계 seed 2 (… / 413) | 324 (−22%) | 395 (−4%) | **404 (−2%)** |
| 덜 배정한 문제 seed 1 / 2 | 51 / 46 | 20 / 17 | **8 / 9** |

- 해석: 덜 배정하는 문제는 거의 풀렸고(−22% → −2%), 비용 차이도 +20~30% → +8% 안팎. **그래도 OR-Tools 를 넘지 못한다** — 이 크기(4~12건)에서는 OR-Tools 가 묶음 후보를 모두 세어 거의 최적이라 학습 모델이 같아지는 것이 상한에 가깝다. 결정(넘을 때 켠다)대로 **LAN 에서는 계속 끈다**.
- 가중치 `models/rf-pmart-l2.ckpt`(6.7MB)는 PC 5 에만 있다(git 제외 — 이미지에 넣을 때 Dockerfile 을 바꾼다). 다시 만들기: `uv run python tools/finetune.py --steps 3000 --route-cost 2.0 --out models/rf-pmart-l2.ckpt`.
- 다음 후보: ① 추론 때 다중 시작·좌표 변환 여러 개를 풀고 우리 비용식으로 가장 좋은 것 고르기(학습 없이, 계산 시간 몇 배), ② 라이더 수를 입력으로 넣는 학습(모델 구조 변경), ③ 실제 카카오 도로 시간 문제로 다시 평가, ④ 큰 MFC(20건 이상)처럼 OR-Tools 가 느려지는 크기에서 비교 — AI 의 장점은 거기서 나올 수 있다.

## 큰 MFC(배송 20~40건)·다중 시작 비교 (2026-11-13 밤, PC 5 — 사용자 "추천한대로 해")
- 도구 보강: `tools/evaluate.py --min-n/--max-n/--multistart/--ortools-limit`. OR-Tools 쪽을 dispatch Java(`OrToolsAssignmentSolver`)와 똑같이 — 규칙 기반 해(`BundleProblem.greedy` 와 같은 순서)를 힌트로 넣고, 시간 안에 해를 못 찾으면 그 규칙 기반 해를 쓴다(처음 돌린 결과는 이 처리가 없어 OR-Tools 배정 수가 쓰레기 값이었다 — 버림). 후보는 dispatch 와 같이 1~3건 모든 묶음·모든 방문 순서, CP-SAT 1 작업자 2초.
- 다중 시작(`RouteFinderModel(multistart=True)`, 서버 기본 켬 `OPTIMIZER_MULTISTART`): 고객마다 출발점을 바꿔 n개를 배치로 한꺼번에 풀고 추가 학습 비용식(Σ도착 + 2 × 경로 수)으로 가장 싼 답.
- 모델: 추가 학습 λ 2.0(`models/rf-pmart-l2.ckpt`). 학습은 4~12건만 했다.

| | 작은 MFC 4~12건 (seed 1 / 2, 60문제) | 큰 MFC 20~40건 (seed 1 / 2, 30문제) |
|---|---|---|
| OR-Tools 가 2초 안에 해를 못 찾아 규칙 기반 해를 쓴 문제 | 0 / 0 | **27 / 24 (80~90%)** |
| 배정 배송 합계 — RouteFinder 한 번 / 다중 시작 / OR-Tools | 439 / 443 / 448 · 404 / 406 / 413 | **896 / 896 / 854 · 860 / 855 / 807** (+5~7%) |
| 배정 수가 같은 문제 비용 차이 평균 — 한 번 / 다중 시작 | +7.9% / +6.3% · +7.9% / +4.7% | **−8.7% / −10.7% · −9.9% / −12.1%** |
| 계산 시간 중앙(ms) — 한 번 / 다중 시작 / OR-Tools | 14 / 17~18 / 15~20 | 42~46 / 59~68 / 2,500~3,100 (최대 7,500) |

- 해석
  - **작은 MFC**: OR-Tools 가 거의 최적이라 RouteFinder 는 여전히 조금 못하다(덜 배정 1~2%, 비용 +5~6%). 다중 시작이 차이를 줄인다.
  - **큰 MFC(20건 이상)**: dispatch 설정(1 작업자·2초)의 CP-SAT 는 대부분 시간 안에 해를 못 내 규칙 기반 해로 떨어지고, 그때는 **RouteFinder 가 더 많이 배정하고(+5~7%) 비용도 9~12% 낮다**. RouteFinder 는 0.1초 안.
  - OR-Tools 시간에는 Python 후보 만들기가 들어 있어 Java 보다 길다. 다만 "해를 못 찾음"은 CP-SAT 풀이 자체(2초 한도)의 결과라 Java 에서도 같을 가능성이 높다 — **Java 로는 아직 재지 않았다**.
  - 도로 시간은 합성값, 큰 문제는 학습 범위 밖(4~12건) — 그래도 이겼다.
- 결정할 것: ① AI 를 켜는 기준을 "배송 수 20건 이상(또는 OR-Tools 가 시간 안에 못 풀 때)"으로 둘지 — 작은 문제는 OR-Tools, 큰 문제는 AI, ② OR-Tools 자체를 고칠지(작업자 수 늘리기·후보 줄이기) — PC 5 CPU 에 영향.

## Java 로 직접 재기 + OR-Tools 후보 줄이기 (2026-11-13 밤, PC 5 — 사용자 "그 순서로 하자")
순서(사용자 동의): ① Java dispatch 로 큰 문제 직접 재기 → ② OR-Tools 묶음 후보 줄이기 → ③ 그래도 AI 가 나으면 큰 MFC 만 AI.

**① Java 직접(`LargeMfcBenchmarkTest`, `PMART_BENCH=1` 때만 — 운영 설정 1 작업자·2초, Python 과 같은 분포의 다른 난수 문제)**

| | 작은 4~12 (60) | 큰 20~40 seed 1 (30) | 큰 20~40 seed 2 (30) |
|---|---|---|---|
| 규칙 기반으로 떨어짐(모든 조합) | 0 | **21** | **26** |
| 배정(모든 조합 / 규칙 기반만) | 435 / 376 | 746 / 746 | 771 / 771 |
| 후보 묶음 중앙(최대) | 62 (284) | 2,683 (7,699) | 3,215 (7,525) |

→ Python 재현과 같다. 큰 MFC 에서 CP-SAT 는 규칙 기반 해와 똑같은 답만 내면서 판단마다 약 2초를 쓴다.

**② 묶음 후보를 고객마다 가까운 k 명으로(`BundleProblem.candidates(..., neighbors)`, 설정 `pmart.dispatch.bundle-neighbors`)** — 2건은 한쪽이 다른 쪽의 이웃, 3건은 한 고객 기준으로 나머지 둘이 이웃.

| k (Java, 같은 문제) | 작은: 배정·총비용 | 큰 seed 1: 떨어짐·배정·총비용·시간 중앙 | 큰 seed 2: 떨어짐·배정·총비용·시간 중앙 |
|---|---|---|---|
| 0(모든 조합) | 435 · 412,574 | 21 · 746 · 682,572 · 1,978ms | 26 · 771 · 676,856 · 1,689ms |
| **4** | 435 · 415,108(+0.6%) | **0 · 797 · 645,026 · 419ms** | **0 · 846 · 648,542 · 604ms** |
| 6 | 435 · 413,054 | 1 · 786 · 664,579 · 1,301ms | 1 · 832 · 678,526 · 1,632ms |
| 8 | 435 · 412,574 | 2 · 761 · 671,648 · 2,015ms | 4 · 804 · 690,047 · 2,021ms |

→ **k = 4 가 가장 좋다**: 큰 MFC 배정 +7~10%, 총비용 감소, 시간 절반 이하. 작은 MFC 는 배정 같고 비용 +0.6%. 6·8 은 아직 2초 한도에 걸려 덜 좋다. 기본값 4 로 넣었다(설정으로 바꿀 수 있음, 0 = 예전처럼 모든 조합).

**③ 같은 문제로 AI 와 비교(`tools/evaluate.py --neighbors 4 --multistart`)**

| | 작은 seed 1 / 2 | 큰 seed 1 / 2 |
|---|---|---|
| 배정(RouteFinder / OR-Tools k=4) | 443 / 448 · 406 / 413 | 896 / **897** · 855 / **860** |
| 배정 수가 같은 문제 비용 차이 평균(RouteFinder − OR-Tools) | +6.1% · +4.6% | **+6.4% · +7.8%** |
| 계산 시간 중앙(ms, OR-Tools 는 Python 후보 만들기 포함) | 27 / 18 · 18 / 11 | 70 / 799 · 76 / 830 |

→ **후보를 줄인 OR-Tools 가 큰 MFC 에서도 AI 보다 낫다.** 계획대로 ③(큰 MFC 만 AI)은 하지 않는다 — **AI 는 계속 끈다.** AI 의 이점은 계산 시간(0.1초 vs 0.4~0.8초)뿐이다.
