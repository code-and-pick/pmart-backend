# AI 추천 배차 성능 검증 — RouteFinder vs OR-Tools (2026-11-13, PC 5)

ADR-0058 결정 11 "OR-Tools 결과와 비교해 검증한다"(원문 Delivery §2.1 ③ "성능 검증")의 첫 결과.

## 방법
- 도구: `ai-services/delivery-dispatch-optimizer/tools/evaluate.py` (`uv run python tools/evaluate.py --instances 60 --seed <n>`).
- 문제: MFC(강남역 부근) 둘레 약 ±2.8km 에 알뜰배달 4~12건, 라이더 (배송/4)~(배송/2)명(라이더 → MFC 60~900초), 출하 대기 0~600초, 묶음 최대 3건·지연 한도 20분·늦음 가중 2.
- 도로 시간: **합성값**(직선거리 × 1.3 ÷ 5m/s). 실제 카카오 도로 시간이 아니다.
- RouteFinder: 서버 그대로(`planner.plan` + RouteFinder rf-transformer-100, 지연 한도를 시간창으로 넣음).
- OR-Tools: dispatch Java 계산과 같은 방식(알뜰배달 1~3건 후보 + 방문 순서 순열 + 지연 한도, CP-SAT 라이더 ↔ 묶음, 2초).
- 둘 다 같은 비용식(dispatch `BundleProblem`)으로 잰다.

## 결과
| | seed 1 | seed 2 |
|---|---|---|
| 배정한 배송 합계 (RouteFinder / OR-Tools) | 347 / 448 (−23%) | 324 / 413 (−22%) |
| RouteFinder 가 덜 배정한 문제 / 더 배정한 문제 | 51 / 0 | 46 / 0 |
| 배정 수가 같은 문제의 총비용 차이(평균·중앙·최대) | +27.8% · +29.0% · +51.3% (9개) | +21.7% · +20.3% · +44.6% (14개) |
| 2건 이상 묶음 수 | 131 / 159 | 123 / 151 |
| 계산 시간 중앙(ms) | 15.5 / 16.6 | 14.1 / 13.5 |

(시간창 없이 돌린 seed 1 첫 결과도 347 / 448, +26.2% 로 거의 같았다.)

## 해석
- **지금 연결 방식의 RouteFinder 는 OR-Tools 보다 분명히 못하다** — 배송을 20% 넘게 덜 배정하고, 같은 수를 배정해도 비용이 20~30% 높다. 계산 시간은 비슷하다.
- 이유(추정): RouteFinder 는 **차량 수 제한이 없는** VRP 로 학습됐다. 고객을 3건씩 채우지 않고 짧은 경로를 여럿 만든다(묶음 수가 OR-Tools 보다 적다). 우리 문제는 라이더 수가 정해져 있고 라이더마다 MFC 까지 오는 비용이 다르다 — 경로가 라이더보다 많으면 남는 배송이 생긴다. 라이더 짝짓기는 모델 밖(서버 규칙)이라 이 차이를 메우지 못한다.
- 원문 §2.1 ③ "모델별 입력 형식과 문제 환경을 맞추고, 필요하면 추가 학습 후 성능 검증"의 "추가 학습"이 필요한 상태다.

## 다음 후보(결정 필요)
1. LAN 에서 AI 를 **끄고** OR-Tools 로 운영하다가, 추가 학습으로 OR-Tools 를 넘으면 켠다(추천 — `pmart.dispatch.ai.base-url` 을 비워 두면 된다).
2. 원문대로 지금 켠다 — 배정이 덜 되면 배송이 다음 판단·재요청으로 밀린다(배차 지연).
3. 추가 학습(fine-tuning): 우리 문제 모양(라이더 수 제한·라이더별 출발 비용·최대 3건·20분 한도)으로 RouteFinder 를 다시 학습 — PC 5 GPU(RTX 2060 6GB, ollama 와 나눠 씀). 학습 데이터 생성기·평가는 이 도구를 늘려 쓴다.
4. GreedRL 비교(원문 후보 — 픽업·배송 문제를 직접 다룬다).

## 추가 학습 결과 (2026-11-13 저녁, PC 5 — 사용자 "추가학습해")
- 도구: `ai-services/delivery-dispatch-optimizer/tools/finetune.py`. **보상만 바꿨다**: 공개 가중치는 열린 경로 길이 합을 줄이도록 배워 1건 경로를 많이 만든다 → 비용 = Σ고객 도착(MFC 출발부터) + λ × 경로 수(경로 = 라이더 한 명). 문제는 서버 추론과 같은 방식(평가 도구 분포, `_normalize`, `planner._deadlines` 시간창, 용량 1/3, 열린 경로). POMO 다중 시작 REINFORCE(같은 문제 평균 기준선), 공개 가중치에서 시작, Adam 1e-5, 배치 64, 3000 단계, **CPU 4스레드 약 17분**(GPU·ollama 안 씀). 검증(고정 문제 126개 탐욕 디코딩)이 가장 좋았던 가중치를 저장.
- 학습 문제 seed 7·검증 1234, 아래 평가는 seed 1·2(처음 검증과 같은 문제).

| | 학습 전 | λ 1.0 | **λ 2.0** |
|---|---|---|---|
| 배정 배송 합계 seed 1 (RouteFinder / OR-Tools 448) | 347 (−23%) | 425 (−5%) | **439 (−2%)** |
| 배정 배송 합계 seed 2 (… / 413) | 324 (−22%) | 395 (−4%) | **404 (−2%)** |
| 덜 배정한 문제 seed 1 / 2 | 51 / 46 | 20 / 17 | **8 / 9** |
| 배정 수가 같은 문제 비용 차이 평균 seed 1 / 2 | +27.8% / +21.7% | +7.9% / +6.1% | +7.9% / +7.9% |
| 같은 문제 중앙 seed 1 / 2 | +29.0% / +20.3% | +4.9% / +1.4% | +4.2% / +6.0% |
| 2건 이상 묶음 seed 1 / 2 (OR-Tools 159 / 151) | 131 / 123 | 155 / 147 | 152 / 141 |
| 계산 시간 중앙(ms) | 15 | 14~15 | 14 |

- 해석: 덜 배정하는 문제는 거의 풀렸고(−22% → −2%), 비용 차이도 +20~30% → +8% 안팎. **그래도 OR-Tools 를 넘지 못한다** — 이 크기(4~12건)에서는 OR-Tools 가 묶음 후보를 모두 세어 거의 최적이라 학습 모델이 같아지는 것이 상한에 가깝다. 결정(넘을 때 켠다)대로 **LAN 에서는 계속 끈다**.
- 가중치 `models/rf-pmart-l2.ckpt`(6.7MB)는 PC 5 에만 있다(git 제외 — 이미지에 넣을 때 Dockerfile 을 바꾼다). 다시 만들기: `uv run python tools/finetune.py --steps 3000 --route-cost 2.0 --out models/rf-pmart-l2.ckpt`.
- 다음 후보: ① 추론 때 다중 시작·좌표 변환 여러 개를 풀고 우리 비용식으로 가장 좋은 것 고르기(학습 없이, 계산 시간 몇 배), ② 라이더 수를 입력으로 넣는 학습(모델 구조 변경), ③ 실제 카카오 도로 시간 문제로 다시 평가, ④ 큰 MFC(20건 이상)처럼 OR-Tools 가 느려지는 크기에서 비교 — AI 의 장점은 거기서 나올 수 있다.
