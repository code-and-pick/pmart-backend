# AI 추천 배차 성능 검증 — RouteFinder vs OR-Tools (2026-11-13, PC 5)

ADR-0058 결정 11 "OR-Tools 결과와 비교해 검증한다"(원문 Delivery §2.1 ③ "성능 검증")의 첫 결과.

## 방법
- 도구: `ai-services/delivery-dispatch-optimizer/tools/evaluate.py` (`uv run python tools/evaluate.py --instances 60 --seed <n>`).
- 문제: MFC(강남역 부근) 둘레 약 ±2.8km 에 알뜰배달 4~12건, 라이더 (배송/4)~(배송/2)명(라이더 → MFC 60~900초), 출하 대기 0~600초, 묶음 최대 3건·지연 한도 20분·늦음 가중 2.
- 도로 시간: **합성값**(직선거리 × 1.3 ÷ 5m/s). 실제 카카오 도로 시간이 아니다.
- RouteFinder: 서버 그대로(`planner.plan` + RouteFinder rf-transformer-100, 지연 한도를 시간창으로 넣음).
- OR-Tools: dispatch Java 계산과 같은 방식(알뜰배달 1~3건 후보 + 방문 순서 순열 + 지연 한도, CP-SAT 라이더 ↔ 묶음, 2초).
- 둘 다 같은 비용식(dispatch `BundleProblem`)으로 잰다.

## 해석
- **지금 연결 방식의 RouteFinder 는 OR-Tools 보다 분명히 못하다** — 배송을 20% 넘게 덜 배정하고, 같은 수를 배정해도 비용이 20~30% 높다. 계산 시간은 비슷하다.
- 이유(추정): RouteFinder 는 **차량 수 제한이 없는** VRP 로 학습됐다. 고객을 3건씩 채우지 않고 짧은 경로를 여럿 만든다(묶음 수가 OR-Tools 보다 적다). 우리 문제는 라이더 수가 정해져 있고 라이더마다 MFC 까지 오는 비용이 다르다 — 경로가 라이더보다 많으면 남는 배송이 생긴다. 라이더 짝짓기는 모델 밖(서버 규칙)이라 이 차이를 메우지 못한다.
- 원문 §2.1 ③ "모델별 입력 형식과 문제 환경을 맞추고, 필요하면 추가 학습 후 성능 검증"의 "추가 학습"이 필요한 상태다.

## 다음 후보(결정 필요)
1. LAN 에서 AI 를 **끄고** OR-Tools 로 운영하다가, 추가 학습으로 OR-Tools 를 넘으면 켠다(추천 — `pmart.dispatch.ai.base-url` 을 비워 두면 된다).
2. 원문대로 지금 켠다 — 배정이 덜 되면 배송이 다음 판단·재요청으로 밀린다(배차 지연).
3. 추가 학습(fine-tuning): 우리 문제 모양(라이더 수 제한·라이더별 출발 비용·최대 3건·20분 한도)으로 RouteFinder 를 다시 학습 — PC 5 GPU(RTX 2060 6GB, ollama 와 나눠 씀). 학습 데이터 생성기·평가는 이 도구를 늘려 쓴다.
4. GreedRL 비교(원문 후보 — 픽업·배송 문제를 직접 다룬다).

## 큰 MFC(배송 20~40건)·다중 시작 비교 (2026-11-13 밤, PC 5 — 사용자 "추천한대로 해")
- 도구 보강: `tools/evaluate.py --min-n/--max-n/--multistart/--ortools-limit`. OR-Tools 쪽을 dispatch Java(`OrToolsAssignmentSolver`)와 똑같이 — 규칙 기반 해(`BundleProblem.greedy` 와 같은 순서)를 힌트로 넣고, 시간 안에 해를 못 찾으면 그 규칙 기반 해를 쓴다(처음 돌린 결과는 이 처리가 없어 OR-Tools 배정 수가 쓰레기 값이었다 — 버림). 후보는 dispatch 와 같이 1~3건 모든 묶음·모든 방문 순서, CP-SAT 1 작업자 2초.
- 다중 시작(`RouteFinderModel(multistart=True)`, 서버 기본 켬 `OPTIMIZER_MULTISTART`): 고객마다 출발점을 바꿔 n개를 배치로 한꺼번에 풀고 추가 학습 비용식(Σ도착 + 2 × 경로 수)으로 가장 싼 답.
- 모델: 추가 학습 λ 2.0(`models/rf-pmart-l2.ckpt`). 학습은 4~12건만 했다.

| | 작은 MFC 4~12건 (seed 1 / 2, 60문제) | 큰 MFC 20~40건 (seed 1 / 2, 30문제) |
|---|---|---|
| OR-Tools 가 2초 안에 해를 못 찾아 규칙 기반 해를 쓴 문제 | 0 / 0 | **27 / 24 (80~90%)** |
| 배정 배송 합계 — RouteFinder 한 번 / 다중 시작 / OR-Tools | 439 / 443 / 448 · 404 / 406 / 413 | **896 / 896 / 854 · 860 / 855 / 807** (+5~7%) |
| 배정 수가 같은 문제 비용 차이 평균 — 한 번 / 다중 시작 | +7.9% / +6.3% · +7.9% / +4.7% | **−8.7% / −10.7% · −9.9% / −12.1%** |
| 계산 시간 중앙(ms) — 한 번 / 다중 시작 / OR-Tools | 14 / 17~18 / 15~20 | 42~46 / 59~68 / 2,500~3,100 (최대 7,500) |

- 해석
  - **작은 MFC**: OR-Tools 가 거의 최적이라 RouteFinder 는 여전히 조금 못하다(덜 배정 1~2%, 비용 +5~6%). 다중 시작이 차이를 줄인다.
  - **큰 MFC(20건 이상)**: dispatch 설정(1 작업자·2초)의 CP-SAT 는 대부분 시간 안에 해를 못 내 규칙 기반 해로 떨어지고, 그때는 **RouteFinder 가 더 많이 배정하고(+5~7%) 비용도 9~12% 낮다**. RouteFinder 는 0.1초 안.
  - OR-Tools 시간에는 Python 후보 만들기가 들어 있어 Java 보다 길다. 다만 "해를 못 찾음"은 CP-SAT 풀이 자체(2초 한도)의 결과라 Java 에서도 같을 가능성이 높다 — **Java 로는 아직 재지 않았다**.
  - 도로 시간은 합성값, 큰 문제는 학습 범위 밖(4~12건) — 그래도 이겼다.
- 결정할 것: ① AI 를 켜는 기준을 "배송 수 20건 이상(또는 OR-Tools 가 시간 안에 못 풀 때)"으로 둘지 — 작은 문제는 OR-Tools, 큰 문제는 AI, ② OR-Tools 자체를 고칠지(작업자 수 늘리기·후보 줄이기) — PC 5 CPU 에 영향.

## 실제 카카오 도로 시간으로 다시 비교 (2026-11-13 밤, PC 5 — 사용자 "실제 카카오 도로 시간으로 다시 비교해")

- **카카오 도로 시간 ÷ 합성값(MFC → 고객)**: 중앙 1.31, 10% 0.92, 90% 1.99 — 합성값(직선 × 1.3 ÷ 5m/s)이 실제보다 짧고 들쭉날쭉하다(일방통행·우회).
- 해석: 실제 도로에서는 AI 와 OR-Tools 차이가 **더 벌어진다**(합성: 덜 배정 1~2%·비용 +5~6% → 카카오: −3%·+11%). AI 는 합성 도로로 학습했고, OR-Tools 는 실제 도로 시간을 그대로 쓰므로 당연한 결과. **AI 는 계속 끈다.** 실제 도로로 다시 학습하려면 카카오 호출이 아주 많이 필요하다(아래 사용량).
- **큰 MFC(20~40건)는 못 돌렸다** — 작은 비교·시험 뒤 큰 비교 중간에 카카오모빌리티 **일 사용량 초과**("API limit has been exceeded", 400 code -10). 사용량이 풀린 뒤 같은 명령으로 이어서 돌리면 저장분은 다시 부르지 않는다(멈춘 시점 이전 구간이 저장되도록 고침 — 처음 멈춘 실행분은 저장 전이라 잃음).
- 주의: 이 키는 LAN delivery-tracking 의 카카오모빌리티 키와 같은 원본이다(`other-pcs-todo` PC 5 절). 오늘 남은 사용량을 다 써서 **LAN 에서 거리 행렬(`POST /internal/distance-matrix`)이 오늘 429/오류일 수 있다** — 지금은 dispatch 가 LAN 에 없어 부르는 곳이 거의 없다. 평가용 키를 따로 받는 것을 권한다.

## 큰 MFC 실제 카카오 도로 비교 (2026-11-14, PC 5 — 사용자 "키를 새로 발급해도 사용량은 똑같으니까 효율성 있게 사용해")
- 사용량: 카카오모빌리티 가격표(developers.kakaomobility.com/price) 일일 무료 제공량 — **다중 목적지 자동차 길찾기 1,000건**(자동차 길찾기 10,000건). 건 단위는 적혀 있지 않지만 유료 표가 "요청 건당"이라 요청 단위로 본다. LAN tracking 과 같은 API·같은 키라 이 1,000건을 나눠 쓴다.
- 아끼는 방법(`--pool 45 --max-calls 120`): 점 45개의 MFC → 점·점 ↔ 점 도로 시간을 **한 번만** 받고(호출 2 + 45×2 = **92번**, 구간 2,025개), 문제 40개는 그 안에서 20~40개를 뽑는다(더 부르지 않음). 문제끼리 점을 나눠 쓰는 대신 라이더 수·라이더 → MFC 시간·출하 대기는 문제마다 다르다. `--max-calls` 를 넘기 전에 멈춘다.
- 명령: `uv run python tools/evaluate.py --instances 40 --seed 1 --min-n 20 --max-n 40 --multistart --neighbors 4 --road kakao --pool 45 --max-calls 120 --kakao-key-file …`

| 큰 MFC 20~40건, seed 1, 40문제(카카오) | RouteFinder | OR-Tools(이웃 4) |
|---|---|---|
| 배정 배송 합계 | 1,039 (**−7.5%**) | 1,123 |
| 덜 / 더 배정한 문제 | **30** / 0 | |
| 배정 수가 같은 10문제 비용 차이 | 평균 **+18.5%**, 중앙 +17.5%, 최대 +27.3% | 기준 |
| 2건 이상 묶음 | 375 | 391 |
| 계산 시간 중앙 / 최대(ms) | 67 / 174 | 744 / 2,218 |

- 카카오 ÷ 합성(MFC → 고객): 중앙 1.49, 10% 1.10, 90% 2.16.
- **결론: 큰 MFC 에서도 실제 도로에서는 OR-Tools 가 훨씬 낫다**(합성 큰 MFC: 배정 거의 같고 비용 +6~8% → 카카오: 배정 −7.5%·비용 +18.5%). 작은 MFC(−3%·+11%)보다 차이가 더 크다. **AI 는 계속 끈다**(`pmart.dispatch.ai.base-url` 비움). AI 의 이점은 계산 시간(0.07초 vs 0.7초)뿐이고, OR-Tools 도 2초 한도 안이다.
- 함께 고친 것: 실제 일 사용량 초과 응답은 429 가 아니라 **400 `{"code":-10}`** 이었다 — delivery-tracking 이 이것을 503 으로 돌려 dispatch 가 5분이 아니라 30초마다 다시 불렀다. tracking `KakaoMobilityClient` 가 400 code -10 → 429 QUOTA_EXCEEDED(dispatch quota-backoff 5분).

## 실제 카카오 도로로 추가 학습·비교 (2026-11-14 저녁, PC 5 — 사용자 "오늘 카카오 사용량 다 쓸 때까지 또 카카오 테스트하고 추가학습하고 비교해")
- **데이터**(`tools/kakao_pool.py` — 줄 단위로 받다가 사용량이 떨어지면 다 받은 줄까지만 묶음): 강남 MFC 둘레 점 **150개**(카카오 755번), 마포 MFC(37.5563,126.9220) 둘레 점 **60개**(약 115번), 마지막 30번에서 **일 사용량 소진**(400 code -10) — 오늘 카카오 약 990번(낮 92번 포함). 합성 좌표만 보냄(고객·라이더 위치 아님). 묶음은 `.cache/`(git 제외).
- **나눔**: 강남 점 0~94 학습, 95~114 검증(저장 판단), **115~149 평가**(학습에 안 쓴 점), **마포 60개 평가**(학습에 안 쓴 지역).
- **학습**(`tools/finetune.py --pool-file … --train-slice 0:95 --val-slice 95:115`): 보상을 직선 평면거리 대신 **카카오 도로 시간 행렬**(평면 단위 — `planner._road`)로 잰 Σ도착 + λ(2.0) × 경로 수. 지난 학습본(`rf-pmart-l2`)에서 이어 3,000단계(배치 32, 고객 4~12, 스레드 2, 약 15분) → 검증 비용 12.97 → **12.57(−3.1%, 1,500단계)** → `models/rf-pmart-road.ckpt`(git 제외).
- **함께 바꾼 서버 코드**:
  1. 다중 시작 답 고르기를 직선 대신 **도로 시간**으로(`planner._road` → `RouteFinderModel(road=)`, `OPTIMIZER_ROAD_SELECT=0` 이면 예전처럼).
  2. **버그 고침 — 모델 시간창이 MFC 직선거리보다 작으면 디코딩이 끝나지 않는다**: 도로 초 → 평면 환산을 지역 중앙값 비율로 하므로 도로가 직선보다 유난히 짧은 고객(강남 묶음 1,576명 중 2명)은 시간창이 바로 가는 거리보다 작아져 영영 방문 못 함 → 학습 한 단계가 메모리 20GB(PC 메모리 부족으로 두 번 멈춤). 서버 추론도 같은 길이라 AI 를 켜면 요청이 멈출 수 있었다. `_deadlines` 가 직선거리 × 1.05 밑으로 내려가지 않게 — 뒤 학습 최대 메모리 1.3GB.

- **해석**:
  - 추가 학습의 큰 효과는 그대로다(공개 가중치 대비 덜 배정 −20% → −5% 안팎).
  - **도로 시간으로 답 고르기**는 작지만 늘 낫다(강남: 배정 +1~5, 비용 −0.7~2.3%p).
  - **실제 도로로 다시 학습한 것은 학습한 지역(강남)에서만 조금 낫고**(큰 MFC 배정 −1.3% → −0.4%, 비용 +9.4% → +9.0%), **처음 보는 지역(마포)에서는 같거나 조금 나쁘다** — 점 95개 한 지역으로는 일반화되지 않는다. 지역마다 학습하려면 지역마다 카카오 수백 번이 든다.
  - **어느 경우에도 OR-Tools 가 배정이 같거나 많고 비용이 6~14% 낮다. AI 는 계속 끈다.**
- 남은 것: 라이더 수를 입력으로 넣는 구조 변경, 여러 지역 데이터(하루 1,000건 — 날마다 조금씩), GreedRL 비교. 서버 쪽 두 변경(도로 고르기·시간창 하한)은 AI 를 켤 때를 위해 넣어 둔다(PR).
